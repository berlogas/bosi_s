# План исправления вкладки «Проекты»

**Статус:** P0 выполнен (2026-11-12). P1 и P2 — не начаты.
**Дата анализа:** 2026-11-11
**Основание:** жалоба «не вижу вывод текстов, которые генерируются для разделов статьи».

> **Что сделано в P0** (подробности — в разделе 6):
> текст раздела теперь приходит из API и открывается **в редакторе** прямо в аккордеоне
> разделов; ручная правка сохраняется в обе модели; история версий отдаёт текст и не падает;
> панель «История» показывает настоящие генерации вместо мока; тесты вкладки переписаны
> под текущий интерфейс (14/14 зелёные). Интерфейс не переделывался — аккордеоны, кнопки
> и порядок экрана остались как были.

---

## 1. Корневая причина

В рабочем дереве лежит незавершённый рефакторинг `webapp/src/features/projects/ProjectsTab.tsx`
(−1488 строк): старая модель «раздел = строка в `project.sections` с редактором» заменена
на новую «раздел = `SectionPlan` + `SectionVersion`».

- **Старая модель** читала `GET /sections` (там лежит текст) и рендерила `CodeMirrorSection`
  на каждый раздел — текст был виден и редактируем.
- **Новая модель** читает только `GET /section-plans`, а текст показывает **из локального
  состояния React** (`genResult` в `SectionsList.tsx:98`) — то есть только до перезагрузки
  страницы.

Бэкенд при этом текст сохраняет корректно (`SectionVersion.content_md`), но API его наружу
не отдаёт, а UI его не запрашивает.

### Живая проверка (проект `95e827bc` — единственный с реальным наполнением)

| Что | Значение |
|---|---|
| `section_plans` | **0 записей** → в UI список разделов пуст |
| `project.sections` | Introduction 3106, Methods 4044, Results 3332, Discussion 1765, Conclusions 2044 симв. |
| `project_versions` | 10 записей с текстом (2565–4044 симв.) |
| `GET /progress` | 5/5, 1922 слова, **100 %** |
| `GET /export?fmt=markdown` | 14 729 байт, текст есть |

Проект полностью готов, прогресс 100 %, экспорт работает — а в UI не видно **ни одного** раздела.
Остальные 7 проектов: `plans=0` или `plans=1` с `current_version=null` → там тоже пусто.

> После P0 у этого проекта 5 планов, и в каждом `current_version.content_md` — текст
> (3106 / 4044 / 3332 / 1765 / 2044 симв.). Редактор показывает его сразу.

## 2. Найденные изъяны

### 2.1. Критичные

1. **Текст не восстанавливается после перезагрузки.**
   `webapp/src/features/projects/components/SectionsList.tsx:98` рендерит только `genResult`
   (локальный `useState`). В БД текст есть (`SectionVersion.content_md`), но UI его ни разу
   не запрашивает.

2. **API прячет текст.**
   - `backend/app/api/projects.py:381-387` — `list_section_plans` отдаёт `current_version`
     **без `content_md`**;
   - `backend/app/api/projects.py:609-622` — `serialize_node` в `/section-plans/{id}/history`
     отдаёт версию **без `content_md`**, и **`all_versions` в ответе отсутствует вообще**,
     хотя TS-тип `VersionTree` его требует (`webapp/src/api/types.ts:251`);
   - эндпоинта «отдать текст версии» нет.

3. **Формат узла дерева не совпадает с типом → UI падает.**
   API отдаёт плоский узел `{id, language, word_count, status, quality_report, created_at,
   created_by, parent_version_id, children}`, TS-тип ждёт `{version: SectionVersion, children}`.
   `VersionTreeView.tsx:41-42` обращается к `node.version.id` → `TypeError` при любой версии.
   Панель «История версий» падает целиком.

4. **Моки вместо данных.**
   `GenerationHistoryPanel.tsx:26` — 3 hardcoded-пункта с комментарием «Пока моковые данные

### 6.4. Сопутствующие починки (2026-11-12)

**`ChatTab.tsx` — удаление пары сообщений было сломано.** В `onMutate` вызывался
`saveState`, которого в компоненте не было (`ReferenceError` в рантайме), а сам
`onMutate` ничего не возвращал — из-за этого `onError` получал пустой контекст
и не откатывал список сообщений. Кнопка «🗑» **не вызывала удаление вовсе**
(только гасила задачу), а блок с ошибкой задачи и модалка очистки переписки
были продублированы — по два раза на экране. Подключён `useSaveState(sessionId)`,
`onMutate` возвращает `{ previous }`, кнопка зовёт `deleteMessage.mutate()`,
дубликаты убраны.

**Кэш генерации разделов не срабатывал никогда.** Язык сравнивался как
«как просили» (`None`) и «как вышло» (`'ru'`): в версию попадало разрешённое
значение, а в запросе оставалось `None` — сравнение всегда давало ложь. Язык
теперь разрешается один раз, в начале `generate_section`
(`request.language or project.language`), и ключ кэша состоит из раздела,
вопроса, языка и **вида генерации** (раньше вид не входил в ключ, и ответ
«обсуждения» мог быть отдан как «раздел»). Заодно вопрос пишется в версию до
генерации: в ветке «источников нет» он раньше сохранялся от прошлого запроса.

**`DangerZone` не открывал модалку, если триггер передан как `children`.**
`onClick` вешался только на кнопку по умолчанию, поэтому **удалить резервную
копию и сбросить состояние из интерфейса было невозможно** — кнопки просто
ничего не делали. Теперь `children` клонируется с `onClick`.

**Кнопка «Сбросить…» была заблокирована навсегда.** Фраза подтверждения

### 6.7. P2 — единая модель хранения (2026-11-12)

**Новая модель (`section_plans` + `section_versions`) — источник истины.**
Старая (`projects.sections`, `project_versions`) осталась зеркалом: её пишут,
но больше не читают.

Новый модуль `backend/app/services/project_sections.py` — единственная точка,
где берутся разделы проекта:

- `project_sections(project)` — разделы с текстом из планов и их текущих версий;
  пока планов нет (проект до перехода) — откат на старую модель, чтобы переход
  можно было делать по частям;
- `current_version(plan)` — текущая версия плана;
- `citation_entries(project)` — записи цитат для списка литературы.

Через него переведены: прогресс проекта, список разделов (`GET /sections`),
разбор черновика, промпты обсуждения и отчёта, указания автора к разделу,
перевод раздела, выгрузка (markdown / docx / zip) и сборка манускрипта.

**`GET /manuscript` больше не пишет в базу.** Раньше сборка манускрипта сама
создавала планы разделов — обычный просмотр менял состояние проекта. Теперь
перенос делает явное действие: `POST /section-plans/sync` или скрипт
`backend/scripts/sync_section_plans.py`. Если планов нет, манускрипт собирается
из старой модели (без истории версий).

**Синхронизация стала идемпотентной.** `sync_project_sections_to_plans` больше
не плодит версии: у раздела, у которого уже есть текущая версия, текст не
трогается (правки и генерации живут в новой модели — затирать их старым JSON
нельзя). Скрипт переноса при повторном запуске ничего не меняет.

**План разделов не может остаться неполным.** Перед генерацией и перед
ручной правкой план дополняется недостающими разделами старой модели
(`ensure_section_plans`) — иначе раздел, который ещё не правили, исчез бы из
прогресса и выгрузки.

**Старый путь генерации тоже пишет в новую модель** (`/generate` → и версия
раздела, и зеркало в старом JSON), поэтому обе модели не расходятся.

**Перенесённые версии — одобренные.** Текст из старой модели написан и
закончен, поэтому при переносе версия получает статус «одобрена»: манускрипт
собирается из одобренных версий, и перенесённая статья в него попадает.

### 7.1. `documents.test.tsx` — 9 падений (тест, ~30 минут) — **сделано**

**Причина.** Тест сам удаляет порталы Mantine из DOM:

```tsx
document.querySelectorAll('[data-mantine-shared-portal-node]').forEach((el) => el.remove())
document.querySelectorAll('.mantine-Notifications-root').forEach((el) => el.remove())
```

Но React этими узлами ещё владеет: при размонтировании он пытается удалить
своих детей из контейнера, которого уже нет, → `NotFoundError: The node to be
removed is not a child of this node`. Это **не** дефект `react-dropzone` и не
приложения — ошибку порождает собственная чистка теста.

**Проверено:** копия теста без этих двух блоков проходит 8/9; девятое падение —
гонка (страница ещё показывает скелетон, когда проверка уже выполнена).

**Что сделать**

1. Убрать оба блока `querySelectorAll(...).forEach(el => el.remove())` из
   `beforeEach` и `afterEach` файла `webapp/src/features/documents/documents.test.tsx`.
2. Вместо них чистить уведомления штатным способом: `notifications.clean()`
   (так уже сделано в `admin/maintenance.test.tsx`) — портал при этом остаётся
   на месте, а React не теряет владение узлом.
3. В тесте «архивная сессия: всё только чтение» заменить синхронные
   `getByLabelText` на `await findByLabelText` — страница грузится в два
   запроса (сессия → документы), и проверка успевала выполниться раньше.

**Приёмка:** `npx vitest run src/features/documents/documents.test.tsx` → 9/9.

### 7.3. `tests/test_tasks_sse.py` — файл **зависал** (тест, ~30 минут) — **сделано**

Две несовместимости теста с кодом (сам код здесь прав и работает):

1. **Заглушка потока устарела по сигнатуре.** Эндпоинт зовёт
   `_task_event_stream(user.id, last_seq)` (`app/api/tasks.py:122`), а подмена
   в фикстуре объявлена как `async def stream(user_id: str)` → `TypeError:
   finite_stream.<locals>.stream() takes 1 positional argument but 2 were
   given` → ответ 500 вместо потока. **Правка:** `async def stream(user_id: str,
   last_seq: int | None = None)`.

2. **Причина зависания.** Генератор теперь отдаёт кадр SSE с номером
   (`id: …\ndata: …\n\n` — нужен для `Last-Event-ID`), а `_collect_events`
   считает только кадры, начинающиеся с `"data: "` → ни один не подходит →
   цикл ждёт вечно, файл висит. **Правка:** считать кадры по `"data: " in event`
   (и то же в разборе JSON: `event.split("data: ", 1)[1]`, а не срез от
   начала).

3. **Ловушка с импортом.** Тест делал `from app.api.tasks import
   _task_event_stream` на уровне модуля — подмена атрибута модуля на неё не
   действует (в HTTP-тестах это не мешает: эндпоинт смотрит имя в глобалах
   модуля, а вот прямые вызовы генератора в тестах идут мимо подмены).
   **Правка:** импортировать модуль (`from app.api import tasks as tasks_api`)
   и звать `tasks_api._task_event_stream(...)` — тогда подмена видна везде.
   Имя `tasks` не годится: в одном из тестов есть локальная переменная с
   таким же именем.
