# Эксплуатация boasi_s

Документ для того, кто разворачивает и сопровождает платформу.
Для пользователей — [USER_GUIDE.md](USER_GUIDE.md), для администраторов —
[ADMIN_GUIDE.md](ADMIN_GUIDE.md).

## 1. Требования

| Компонент | Минимум | Комментарий |
| --- | --- | --- |
| Docker + Compose | 24.x / v2 | Проверено на Compose v5 |
| CPU | 4 ядра | Dev-машина: 8 ядер, без GPU |
| RAM | 8 ГБ | Индекс PaperQA держится в памяти процесса |
| Диск | 20 ГБ + модели | Модель `qwen2.5:3b` ~2 ГБ |
| GPU | не требуется | В бою — см. `docker-compose.prod.yml` |

## 2. Первый запуск на новом сервере

```bash
git clone https://github.com/berlogas/bosi_s.git
cd bosi_s

make bootstrap      # .env, SECRET_KEY, том, модели, стек, первый админ
```

`make bootstrap` идемпотентен и делает всё сразу:

1. копирует `.env.example` в `.env`, если файла нет;
2. генерирует `SECRET_KEY`, **только** если там ещё шаблон (перезаписывать
   ключ на работающем сервере нельзя — это отозвало бы все выданные JWT);
3. создаёт том `boasi_data`;
4. скачивает модели Ollama (`make pull-models`);
5. собирает и поднимает стек (`make up --build`) и ждёт `status: ok`;
6. создаёт администратора (пароль спросит, либо задайте `ADMIN_PASSWORD`);
7. кладёт маркер `/data/.install-state.json`.

Без интерактивного ввода (CI, ansible):

```bash
ADMIN_USERNAME=admin ADMIN_PASSWORD='...' make bootstrap
```

Вручную, по шагам, если скрипт не подходит:

```bash
cp .env.example .env
# ОБЯЗАТЕЛЬНО: сгенерировать ключ подписи токенов
python -c "import secrets; print(secrets.token_urlsafe(48))"   # вставить в SECRET_KEY

make pull-models     # скачать модели Ollama (контур работает оффлайн)
make up              # поднять ollama + backend + frontend
make health          # http://127.0.0.1:8000/api/health
make create-admin    # первый админ (регистрации в UI нет)
```

Проверка:

```bash
make health          # http://127.0.0.1:8000/api/health
```

Ожидается `status: ok`, `database: ok`, `ollama.reachable: true`.
Если `ollama.reachable: false` — модель не скачана: `make pull-models`.

URL: <http://127.0.0.1> (порт 80).

> `.env` с `SECRET_KEY` нужно сохранить в секретном хранилище: при его
> потере все выданные токены перестанут проверяться и потребуется новый вход
> для всех пользователей.

## 3. Что где лежит

| Путь | Содержимое | Бэкапится |
| --- | --- | --- |
| том `boasi_data` | **всё состояние** | да |
| `/data/boasi.sqlite3` | пользователи, сессии, документы, сообщения, аудит, чанки PaperQA | да |
| `/data/pqa/` | кэш ответов (состояние PaperQA хранится в БД, не здесь) | да |
| `/data/documents/` | файлы глобальной базы и `incoming/` | да |
| `/data/documents/library/YYYY-MM/` | файлы, импортированные из inbox (на них ссылается БД) | да |
| `/data/inbox/` | **папка-приёмник** для массового добавления (bind-mount `./inbox`) | нет (временная) |
| `/data/rejected/` | файлы, которые не удалось разобрать; чистит человек через UI | да |
| `/data/sessions/<id>/` | файлы документов сессии | да |
| `/data/hf/`, `/data/torch/` | кэш моделей эмбеддингов (HF_HOME, TORCH_HOME) | нет (качаются заново) |
| том `boasi_ollama_models` | скачанные модели Ollama | нет (качаются заново) |

Журнал аудита растёт на каждое действие и убирается reaper'ом: `AUDIT_RETENTION_DAYS`
(по сроку), `AUDIT_MAX_ROWS` (по объёму) и список защищённых
`AUDIT_PROTECTED_ACTIONS`. Подробно — в ADMIN_GUIDE, раздел 6.

Важно: кэш моделей лежит **внутри** тома данных, но сброс состояния его
не трогает — см. раздел 9.

## 4. Бэкап и восстановление

> **На Windows `make` нет в стандартной поставке.** Все команды ниже есть в
> `scripts\boasi.bat` — без `make` и без bash:
>
> ```
> scripts\boasi.bat backup
> scripts\boasi.bat backup-verify backups\boasi-20261008-120000.tar.gz
> scripts\boasi.bat restore backups\boasi-20261008-120000.tar.gz
> scripts\boasi.bat reset-plan
> scripts\boasi.bat help          — полный список команд
> ```
>
> Скрипт сам находит Git Bash (Git for Windows) — в Windows есть три разных
> `bash.exe`, и `.bat` выбирает именно нужный. Положить скрипт в PATH, чтобы
> пользоваться `boasi backup` вместо полного пути.

### Команды

```bash
make backup                                    # -> backups/boasi-YYYYmmdd-HHMMSS.tar.gz
make backup-config                             # + .env c SECRET_KEY, отдельным файлом
make backup-verify ARCHIVE=backups/xxx.tar.gz  # проверить архив, не трогая боевой том
make restore-list ARCHIVE=backups/xxx.tar.gz   # состав и манифест, без распаковки
make restore ARCHIVE=backups/xxx.tar.gz        # восстановление (стек остановлен!)
```

То же самое без `make`:

```
scripts\boasi.bat backup
scripts\boasi.bat backup-verify backups\xxx.tar.gz
scripts\boasi.bat restore backups\xxx.tar.gz
```

### Откуда берём данные

Скрипт сам определяет, где лежят данные:

| Режим | Где лежат данные | Как запустить |
| --- | --- | --- |
| `local` | `data/` в корне репозитория (`DATA_DIR`) | `./scripts/start.sh` — обычный режим |
| `docker` | том `boasi_data` (`/data`) | `./scripts/start.sh docker` или `make up` |

Режим определяется автоматически: если тома `boasi_data` существует и демон Докер подшучен — работаем с локального каталога,
иначе — с томом. Локальный режим не требует Docker вообще.

Принудитьное значение: `BOASI_MODE=local|docker` перед архивом и каталогом.

> Раньше скрипты умели только Docker-том и падали на
> `docker volume create boasi_data`, хотя данные лежат рядом с вами в `data/`. Сейчас
> работает без вместательства, но `make up`/`make down` не делают ничего в
> этом режиме — стопать `scripts/start.sh stop`.

### Что именно снимается

| В архиве | Что это |
| --- | --- |
| `.backup-snapshot.sqlite3` | согласованный снимок БД через `sqlite .backup` |
| `sessions/`, `documents/`, `pqa/` | файлы сессий, документы, кэш ответов |
| `hf/`, `torch/` | кэш моделей эмбеддингов (если есть в томе) |
| `boasi-manifest.json` | ревизия схемы, строки в таблицах, объём, модели |
| `.install-state.json` | метка установки (кладёт `bootstrap.sh`) |

Рядом с архивом — `boasi-<stamp>.tar.gz.sha256`.

**Почему БД снимается снимком, а не «файл + WAL».** Живой `boasi.sqlite3`
и `-wal` читаются в разные моменты: между ними может лечь транзакция, и
такой архив не восстановится. `sqlite .backup` даёт самодостаточный файл,
который кладётся в архив вместо живой БД, а `-wal/-shm` исключаются.
Внутри архива снимок лежит под служебным именем — `restore.sh` кладёт его на
место `boasi.sqlite3`, поэтому архив не зависит от посторонних хвостов WAL.

**Про `.env` и `SECRET_KEY`.** В архив с данными он не входит: такой файл
нельзя ни хранить рядом с бэкапами, ни пересылать. Если переносите платформу
на другой сервер — сохраните `.env` отдельно (`make backup-config`, права 600)
или из секретного хранилища. Без того же `SECRET_KEY` все выданные токены
перестанут проверяться: пользователи просто не смогут войти (данные целы,
access-токены живут 30 минут, но refresh-токены перестанут обновляться).

### Отдельно: копию можно снять из админки

Вкладка **Обслуживание** → **Создать копию**: архив снимается изнутри
процесса (Python, не Docker), поэтому платформа не останавливается и можно снять
на ходу работы пользователя.

Архив получается идентично со скриптовым архивом — им можно восстанавливать.
Каталог — `BACKUP_DIR` (в Docker это отдельный том `/backups`, локально —
`backups/`), ротация — `BACKUP_KEEP`.

### Автоматизация (cron, раз в сутки)

```cron
30 3 * * * cd /opt/bosi_s && KEEP_BACKUPS=14 make backup >> /var/log/boasi-backup.log 2>&1
```

`KEEP_BACKUPS=14` оставляет 14 последних архивов (по умолчанию хранится всё).

### Проверка бэкапа

Делать руками — автомат это не проверит. Отдельная команда
распаковывает архив во временное место, проверяет
`PRAGMA integrity_check`, ревизию схемы, счётчики строк и наличие файлов, потом
удаляет временные данные:

```bash
make backup-verify ARCHIVE=backups/последний.tar.gz
```

Выводит что-то подобное:

```
   [ok] boasi.sqlite3: 684032 байт
   [ok] integrity_check: ok
   [i] ревизия схемы: c4d81f0a7b52
   [i] строк по основным таблицам: 37
   [ok] /sessions: 12 файлов
```

Полная проверка «как на новом сервере» — восстановление в отдельный
каталог (или том) и запуск на нём:

```bash
# локальный режим
./scripts/restore.sh backups/последний.tar.gz --force --target /tmp/proba

# режим Docker
make restore ARCHIVE=backups/последний.tar.gz --force --target boasi_data_staging
BOASI_DATA_VOLUME=boasi_data_staging docker compose up -d
make health
```


### Восстановление

```bash
# локальный режим (данные в ./data)
./scripts/start.sh stop
./scripts/restore.sh backups/xxx.tar.gz      # спросит подтверждение
./scripts/start.sh && ./scripts/start.sh status

# режим Docker (данные в томе)
make down
make restore ARCHIVE=backups/xxx.tar.gz
make up && make health

# в отдельный каталог/том — боевые данные не трогаются
./scripts/restore.sh backups/xxx.tar.gz --target /tmp/proba --force
```

Порядок работы `restore.sh` важен — он специально такой:

1. **сверка sha256** — битый архив отсекается до любых разрушений;
2. **показ состава и манифеста** — видно ревизию схемы и объём;
3. проверка, что платформа остановлена (в локальном режиме — по ответу
   `/api/health`), и подтверждение вручную (или `--force`);
4. **страховочная копия текущих данных** в `backups/pre-restore/` — чтобы
   «восстановил не тот архив» не стоил данных;
5. очистка и распаковка, снимок кладётся на место `boasi.sqlite3`;
6. `PRAGMA integrity_check` на восстановленной БД; при повреждении скрипт
   падает с ненулевым кодом, не объявляя успех.

Если манифест показывает `alembic_revision` старше `alembic_head` — это норма:
после запуска применятся миграции вперёд.

### Перенос на новый сервер

```bash
# на старом сервере
make backup && make backup-config

# на новом: код + .env из секретного хранилища, затем
./scripts/restore.sh backups/boasi-....tar.gz
./scripts/start.sh                          # локальный режим
```

Каталог кэша моделей (`data/hf`, `data/torch`) лежит рядом с данными
и потому попадает в бэкап автоматичны — модель эмбеддингов
заново не нужно. Модели Ollama живут отдельно (в Docker — том
`boasi_ollama_models`) и по умолчанию не копируют (это гигабайты): либо
`MODELS_BACKUP=1 make backup`, либо на новом сервере `make pull-models`.


## 5. Обновление

```bash
make backup                                   # сначала
git pull && make up --build                   # пересборка
```

Миграции применяются автоматически при старте контейнера
(`alembic upgrade head` в CMD). Откат миграций не автоматизирован.

## 6. Модели

`LLM_MODEL` — единственный параметр смены модели. Скорость на dev-машине
не оптимизируется, в бою меняется только значение в `.env`:

```bash
# в бою на GPU-машине
LLM_MODEL=ollama/qwen2.5:14b
make pull-models && make up
```

Код не содержит ни одной константы, завязанной на скорость: `evidence_k`,
`answer_max_sources`, таймауты LLM — только из конфигурации.

## 7. Наблюдаемость

| Что | Где |
| --- | --- |
| Здоровье | `GET /api/health` — статус, БД, модель, доступность Ollama |
| Метрики (Prometheus) | `GET /api/metrics` — текстовый формат |
| Метрики (глазами) | `GET /api/metrics.json` |
| Блокировки | `GET /api/health/locks` |
| Логи | `docker compose logs -f backend` — JSON в stdout |
| Аудит действий | вкладка «Аудит» в админ-панели, таблица `audit_log` |

Логи структурированы: `{"ts", "level", "logger", "msg", ...}`.

Что стоит смотреть в первую очередь при жалобах «медленно»:

```bash
make metrics    # uptime, документы, чанки, активные задачи
```

Медленный ответ — это норма для CPU-инференса (Фаза 0: 1,5–6 минут на ответ
при `qwen2.5:3b`). Смотрите, не выполняется ли вместо одного запроса два.

## 8. Диагностика

| Симптом | Причина | Что делать |
| --- | --- | --- |
| Backend не стартует, в логах про `SECRET_KEY` | ключ короче 32 символов или шаблонный | сгенерировать новый (раздел 2) |
| `/api/health` = `degraded` | недоступна БД | проверить том `boasi_data` и права |
| `ollama.reachable: false` | модель не скачана или сервис не поднят | `make pull-models` |
| Ответ «модель не найдена» | нет `LLM_MODEL` в томе Ollama | `make pull-models` |
| Индекс пуст после рестарта | повреждён `PQA_HOME` | восстановить из бэкапа, затем `make reindex` |
| Долгий логин, 429 | сработал rate-limit | подождать `LOGIN_LOCKOUT_SECONDS` |
| После сброса «не считаются эмбеддинги» | снесён кэш моделей (`--include-models`) | `make warm-embedding` (с моделью из `.env`) |
| После сброса остался старый индекс | не удалён `document_chunks` | `make reset-data` — он чистит его вместе с документами |
| `/api/admin/reset` отвечает 403 | `ENVIRONMENT=prod` без `ALLOW_DESTRUCTIVE_RESET` | осознанно выставить флаг в `.env` |

Частые логи и их смысл:

```bash
docker compose logs backend | grep -E '"level": "(ERROR|WARNING)"' | tail -50
```

## 9. Сброс состояния

Сброс удаляет данные **безвозвратно** — единственный путь назад это бэкап.
До сброса `scripts/reset_state.sh` автоматически снимает бэкап тома
(пропускается при `NO_BACKUP=1`).

### Уровни

| scope | Что удаляется | Что остаётся | Фраза подтверждения |
| --- | --- | --- | --- |
| `data` | сессии, документы, проекты, версии, чанки PaperQA, переписка, файлы | пользователи, аудит | `СБРОС ДАННЫХ` |
| `users` | всё из `data` + все refresh-токены (сбрасывает все входы) | пользователи, аудит | `СБРОС СЕССИЙ` |
| `all` | всё из `users` + таблицы `users` и `audit_log` | только конфигурация | `ПОЛНЫЙ СБРОС` |

### Команды

```bash
make reset-plan                    # план сброса данных, ничего не удаляет
make reset-data                    # scope=data
make reset-users                   # scope=users
make reset-all                     # scope=all (после — make create-admin)
```

Ручной вызов с JSON-выводом и другим scope:

```bash
./scripts/reset_state.sh --scope all --json              # план
./scripts/reset_state.sh --scope data --yes --confirm 'СБРОС ДАННЫХ'
```

Из контейнера напрямую (пути `/data` совпадают с боевыми):

```bash
docker compose run --rm backend python scripts/reset_state.py --scope data
```

### Как это устроено

* Индекс RAG не хранится на диске — PaperQA восстанавливает его из таблицы
  `document_chunks`, поэтому чистки БД достаточно;
* `document_chunks` очищается **вместе** с документами, иначе после сброса
  `restore_state()` поднимет старый индекс (и он будет противоречить БД);
* `refresh_tokens` — opaque-значения, а не JWT: их удаление обязательно, иначе
  сессии пользователей переживут сброс (JWT при этом инвалидируются новым
  `SECRET_KEY` сами);
* сброс пишется в `audit_log` **до** удаления, а при `scope=all` — ещё раз
  после, иначе запись исчезла бы вместе с таблицей;
* скелет каталогов (`sessions/`, `documents/`, `pqa/`) пересоздаётся, из
  памяти выбрасываются индекс PaperQA, задачи, локи и кэш ответов.

### Кэш моделей не трогаем

`HF_HOME=/data/hf` и `TORCH_HOME=/data/torch` лежат **внутри тома данных**,
но сброс их не удаляет: иначе оффлайн-контур останется без модели
эмбеддингов, пока её не скачают заново. Обойти это можно только явно:

```bash
./scripts/reset_state.sh --scope all --include-models --yes --confirm 'ПОЛНЫЙ СБРОС'
make warm-embedding    # после этого модель эмбеддингов качается заново
```

### Защита

* по умолчанию выполняется только план; удаление требует `--yes` и точной фразы;
* в `prod` сброс запрещён, пока в `.env` не выставлено
  `ALLOW_DESTRUCTIVE_RESET=true`; само значение даёт предупреждение при старте;
* из UI то же самое: вкладка **Сброс** в админке требует ввести фразу.

## 10. Безопасность (hardening)

Что включено:

* `SECRET_KEY` обязателен: короткий или шаблонный — приложение не стартует;
* rate-limit на `/api/auth/login`: неудачных попыток не больше
  `LOGIN_MAX_ATTEMPTS` за `LOGIN_WINDOW_SECONDS` с IP, блокировка на
  `LOGIN_LOCKOUT_SECONDS` (429);
* **валидация путей**: документ нельзя добавить откуда угодно — только из
  каталога своей сессии, общего каталога документов или каталога данных
  (для админа). Симлинки наружу не обходят проверку, `..` не проходит;
* офлайн-режим по умолчанию: нет запросов к Crossref/Semantic Scholar;
* `multimodal=OFF`, приватность данных: наружу уходит только к вашему Ollama;
* пароли — argon2 (`pwdlib`), refresh-токены в БД только в виде хэша;
* доступ к БД и фронтенду — только с `127.0.0.1`.

Что стоит настроить перед боевым режимом:

```bash
ALLOW_EXTERNAL_IMPORT_PATHS=false   # оставить выключенным
OFFLINE_MODE=true
MULTIMODAL=false
LOG_LEVEL=INFO                     # WARNING в проде, если логов много
```

Если нужен импорт файлов из произвольных мест (например, с сетевого диска) —
`ALLOW_EXTERNAL_IMPORT_PATHS=true`, но файлы всё равно не выйдут за пределы
каталога данных. Приложение предупредит об этом в логах при старте.

## 11. Боевой режим (GPU)

Настройки производительности под боевой режим и их замеры — §12.2
(`EVIDENCE_SKIP_SUMMARY`, `EVIDENCE_K`, `MAX_CONCURRENT_REQUESTS`).

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d
```

prod-оверрайд добавляет: GPU passthrough для Ollama (NVIDIA, все карты),
`OLLAMA_KEEP_ALIVE=24h`, лимиты ресурсов, ротацию логов, `restart: always`.

Перед боевым запуском: смените `LLM_MODEL` на модель по объёму VRAM,
сгенерируйте `SECRET_KEY`, сделайте бэкап.

`ALLOW_DESTRUCTIVE_RESET` в бою по умолчанию `false`: сброс состояния на
рабочем сервере должен быть осознанным решением, а не случайной кнопкой.
Если он нужен регулярно (например, после переноса на новый сервер) — включите
явно и задокументируйте в регламенте.

## 12. Профилирование ответа

Время ответа зависит от числа сетевых вызовов, а не от размера базы: один вызов
LLM на каждый фрагмент, попавший в выдачу. Поэтому «медленно» обычно означает
«много фрагментов и часть вызовов впустую». Разложить ответ по этапам:

```bash
cd backend
../.venv/Scripts/python.exe scripts/profile_answer.py "вопрос" \
    --session-id d5749433-9... --repeat 3
```

Ключи: `--mode` (`hybrid`/`session_only`/`global_only`/...), `--k`,
`--max-sources`, `--repeat`. Кэш ответов обходится, иначе повторный замер
покажет время чтения из кэша, а не работы. LLM недетерминирован — поэтому
`--repeat 3` полезнее одного прогона: разброс бывает в разы.

Что показывает вывод:

| Строка | Смысл |
| --- | --- |
| `сводки <коллекция>` | время сводки фрагментов этой коллекции. Помечены `(параллельно)`: коллекции обрабатываются одновременно, их времена **не складываются** |
| `evidence (сводки + rerank)` | весь этап поиска по стенным часам |
| `генерация ответа` | один вызов LLM с собранным контекстом |
| `постобработка` | цитаты и grounding, локально, обычно доли секунды |

В колонке `->` — число контекстов, прошедших порог релевантности. **Ноль при
ненулевом времени означает потраченное впустую время:** LLM вернула оценку 0, и
paperqa отбросил все контексты. Затем срабатывает fallback (повтор без сводок,
релевантность по эмбеддингам) — об этом говорит префикс `evidence [повтор без
сводок]` в логе backend.

Восстановление коллекций и эмбеддинг запроса в разбивку не попадают: модель
эмбеддингов кэшируется на процесс (иначе веса читались бы с диска по 12 раз за
запрос), эмбеддинг одного вопроса — десятки миллисекунд.

### 12.1 Отладочный режим (без GPU, облачная LLM)

Быстрые итерации важнее качества, но качество не роняем совсем:

```bash
EVIDENCE_SKIP_SUMMARY=false   # рекомендация PaperQA, см. 12.3
EVIDENCE_K=5                  # меньше фрагментов — меньше вызовов
ANSWER_MAX_SOURCES=8
MAX_CONCURRENT_REQUESTS=4     # по умолчанию PaperQA; 1 было настроено под CPU-Ollama
```

Цена решения известна и измерена (Atria, 28 фрагментов): **65–190 с** на
вопрос, разброс из-за недетерминированности модели. Основная статья — сводки
(до 95% времени); генерация ответа 10–35 с. Если для отладки этого много,
переключайте `EVIDENCE_SKIP_SUMMARY=true`: ответ укладывается в ~25 с, но
релевантность считается только по косинусу эмбеддингов и посторонние фрагменты
в выдачу проходят. Что именно переключать — см. 12.3.

### 12.2 Боевой режим (Ollama на GPU)

Локальная модель меняет всё три пункта, поэтому настройки другие:

```bash
EVIDENCE_SKIP_SUMMARY=false
EVIDENCE_K=10                 # дефолт авторов: локально сводки почти бесплатны
MAX_CONCURRENT_REQUESTS=8     # GPU любит батчи; 4 недогружают карту
```

Ожидаемое время (8B-модель, bf16, A100): **15–25 с** вместо 65–190. Источники
экономии, по убыванию эффекта:

1. **Исчезает сеть.** Облачный вызов стоит 7–10 с (RTT + инференс), локальный —
   сотни миллисекунд. Это и есть основной выигрыш.
2. **Батчи вместо ожидания.** Свободные секунды уходят не в 4 параллельных
   вызова, а в 8–16.
3. **Оценки релевантности становятся осмысленными.** Локальная модель даёт
   непустой `relevance_score`, поэтому fallback почти не срабатывает, а время,
   потраченное впустую, уходит.

Перед боевым запуском замерьте свою модель тем же скриптом — цифры выше
оценка для 8B на A100, а не измерение.

### 12.3 Почему `EVIDENCE_SKIP_SUMMARY` по умолчанию `false`

В алгоритме PaperQA2 (README, «PaperQA2 Algorithm», фаза Gather Evidence) сводка
фрагмента с оценкой релевантности — обязательный шаг, а не опция: фрагменты
идут в LLM, она их суммирует и переоценивает. Дефолт в upstream — `False`,
`prompts.use_json=True`. Отключать сводки стоит только ради скорости, и тогда
релевантность ложится на эмбеддинги — это заметно хуже по качеству на
смешанных корпусах.

Облачные модели это усиливают: при нестабильном `relevance_score` все контексты
отбрасываются по условию `c.score > 0`, и запрос тратит время впустую. Поэтому
в `rag_service._evidence` есть одноразовый fallback: если сводки не дали ни
одного контекста, тот же запрос повторяется без них. Плата — время первого
прохода; выигрыш — не «в базе нет данных», а честный ответ по косинусу.

### 12.4 Порог релевантности: `EVIDENCE_MIN_RELEVANCE_SCORE`

Отсекает слабо релевантные фрагменты; `0` = не отсекать (по умолчанию).
**Шкала 0..1 — это `relevance_score` от LLM, делённый на 10**, то есть ровно
та величина, которой PaperQA оценивает фрагмент. Значение `0.1` соответствует
штатному `answer.evidence_relevance_score_cutoff = 1`; этот порог выставляется
из того же параметра, поэтому фактический отсев — наш (до rerank и отбора
источников) и встроенный (при сборке контекста).

При `EVIDENCE_SKIP_SUMMARY=true` оценки от LLM нет: `score` становится
синтетическим (косинус × 10), и тогда параметр означает порог косинуса.
Название про «релевантность» в обоих случаях честное, но шкалы разные — это
стоит помнить при переносе настроек между режимами.

**Почему выключено.** На корпусе из 9 документов (7 вопросов, 2026-10-12)
диапазоны релевантных и посторонних фрагментов перекрываются: нужные дают
0.84–0.87, посторонние 0.81–0.85, а на вопрос «кем была Екатерина Алексеевна»
посторонний фрагмент оказался релевантнее нужного (0.853 против 0.839). На
таких данных любой абсолютный порог либо пропустит весь мусор, либо срежет
нужное — а второе хуже.

Когда включать: когда база станет заметно больше и разброс релевантностей
вырастет. Проверяйте тем же скриптом профилирования — в колонке `->` видно,
сколько фрагментов пережило порог, и нулевое время при непустом выводе
покажет слишком высокий порог.

## 13. Ограничения

* Один процесс backend: реестр фоновых задач и «аренды» сессий живут в памяти,
  после рестарта незавершённые задачи теряются (их можно поставить заново),
  окно rate-limit обнуляется. Несколько реплик backend не поддерживаются —
  платформа по ТЗ локальная и однопользовательская по контуру.
* SQLite + WAL: рассчитан на один процесс записи, не на высокую конкуренцию.
* Модель эмбеддингов качается из HuggingFace при первом старте. Для полностью
  оффлайн-контура нужен `make warm-embedding` или предзагрузка в том.
