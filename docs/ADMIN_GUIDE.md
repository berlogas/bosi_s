# Администратору boasi_s

Как завести пользователей, наполнить глобальную базу и следить за системой.
Развёртывание — в [OPERATIONS.md](OPERATIONS.md).

## 1. Первый вход

Регистрации в интерфейсе нет — это осознанно: учётные записи создаёт
администратор. Первого админа создаём из командной строки:

```bash
make create-admin
# Логин: admin
# Пароль: не короче 8 символов
```

Войдите на <http://127.0.0.1> → вкладка «Администрирование».

## 2. Пользователи

Вкладка **Пользователи** → «Создать пользователя».

| Роль | Что может |
| --- | --- |
| `researcher` | свои сессии, документы, проекты, чат |
| `admin` | всё выше + глобальная база, все сессии, аудит, управление пользователями |

Действия с существующим пользователем:

* смена роли — выпадающий список + «Сохранить»;
* смена пароля — поле «Новый пароль» (пустое поле = пароль не меняется);
* блокировка — снятие галочки активности (`PATCH` с `is_active=false`).

Удаление пользователя — кнопка «Удалить» в его строке. Подтверждение
предупреждает, что вместе с учётной записью каскадно удаляются его сессии,
сообщения, документы и проекты, и отменить это нельзя. Снять галочку
активности вместо удаления — обратимо, поэтому для «закрыть доступ» она и
предпочтительнее. Перед удалением имеет смысл сделать `make backup`.

Себя удалить нельзя: кнопка у собственной строки задизейблена, а API вернёт 409.

## 3. Глобальная база знаний

Вкладка **Глобальная база**. Здесь документы, доступные **всем** исследователям
(руководства, справочники, общая литература).

Три способа добавить:

1. **Один файл** — путь на диске. Путь должен быть внутри каталога данных
   (например `/data/documents/...`); при желании расширить —
   `ALLOW_EXTERNAL_IMPORT_PATHS=true`.
2. **Загрузка** — перетащите файлы в браузере.
3. **Массовая индексация** — список путей (по одному в строке или через запятую),
   до 200 файлов за раз. Идёт **в фоне**: показывается прогресс по файлам и
   кнопка «Отменить».

> Индексация одного PDF занимает от секунд до нескольких минут (на dev-машине
> это норма — скорость не оптимизируется). Плата: эмбеддинги считаются локально,
> запрос к LLM на этапе добавления не делается.

Переиндексация (после смены модели эмбеддингов или повреждения кэша):
кнопка «Переиндексировать всё». Долгая операция — не закрывайте вкладку.

Удаление документа убирает его и из индекса, и из реестра — ответы перестанут
на него ссылаться.

## 4. Сессии

Вкладка **Сессии** показывает все сессии всех пользователей: кто, когда,
последнее действие. Управление из UI не предусмотрено (своими сессиями
исследователь управляет сам) — это осознанное ограничение, чтобы админ
не мог спутать чужую работу.

## 5. Задачи

Вкладка **Задачи** — все фоновые операции: индексация, вопросы по контексту,
генерация разделов. Видны прогресс, текущий шаг и ошибки. Задачу можно
отменить — работа прервётся на ближаетшем шаге.

Ошибки индексации (`DocumentProcessingError`) чаще всего означают
неподдерживаемый тип файла — сверьтесь со списком `ALLOWED_EXTENSIONS` в `.env`.

## 6. Аудит

Вкладка **Аудит** — журнал действий: кто, что, когда, с какого IP.

Записываются все мутации, все входы (включая неудачные), обращения к глобальной
базе, отмена задач. Запросы на чтение документов **не** пишутся — иначе журнал
разрастался бы быстрее, чем даёт пользу. Если нужно знать, кто что читал, —
это отдельное решение и требует проработки по объёму.

## 7. Обслуживание: копии и сброс

Вкладка **Обслуживание** — две операции, которые лучше не искать по разным
местам: снять копию и стереть платформу.

### Резервные копии

Кнопка **Создать копию** — архив с базой данных (согласованный снимок),
файлами сессий и документов, манифестом с ревизией схемы и контрольной
суммой. Платформа не останавливается — снять можно прямо по работе.

Фразы подтверждения не нужно: операция ничего не
разрушает, худшее — потратится место на диске, и объём показан в окне.

Копии складываются в каталог **за пределами данных** (`/backups` в Docker,
`backups/` локально). Иначе копия попадала бы сама в себя и каждый раз
расти без предела.

Автоматическая ротация: хранится `BACKUP_KEEP` копий (по умолчанию — 14),
при создании новой более старые удаляются. Ненужные копии можно удалить
кнопкой в таблице.

Проверить копию, не распаковывая:

```
scripts\boasi.bat backup-verify backups\boasi-20261008-120000.tar.gz   # Windows
./scripts/verify_backup.sh backups/boasi-20261008-120000.tar.gz       # bash
```

Копия из админки содержит снимок базы в том же формате, что у скриптов.
После нажатия появится уведомление в правой верхней части страницы,
а список перечитывается сам — нажимать «Обновить» не нужно.

### Восстановление — только скриптом

Восстановление требует остановки платформы: база в этот момент уже исчезает,
пока идёт распаковка. Поэтому в браузере его нет, а подсказка в разделе
ведёт к скрипту:

```bash
# Windows
scripts\start.bat stop
scripts\boasi.bat restore backups\boasi-20261008-120000.tar.gz
scripts\start.bat

# bash / Linux
./scripts/start.sh stop
./scripts/restore.sh backups/boasi-20261008-120000.tar.gz
./scripts/start.sh
```

Порядок такой, что «восстановил не тот архив» не стоит данных: скрипт
сначала сверяет контрольную сумму, потом кладёт страховочную копию текущего
состояния в `backups/pre-restore/`, и только затем чистит каталог.

### Сброс состояния

Вторая половина вкладки — те же уровни, что и раньше: от «данные» до «всё».
Единственный путь назад — сброс, сделанный **до** него. Снимите копию заранее.

| Уровень | Что удаляется | Что остаётся |
| --- | --- | --- |
| Данные | сессии, документы, проекты, переписка, файлы, индекс | пользователи, аудит |
| Данные и входы | то же + все refresh-токены (всем нужно войти заново) | пользователи, аудит |
| Всё | то же + учётные записи и аудит | ничего, платформа пуста |

Важно:

* сбрасываются и сообщения в чате, и черновики проектов, и загруженные файлы —
  восстановить их можно только из копии;
* **«Также удалить кэш моделей»** обычно трогать не надо: без него платформа
  останется работать в офлайне; если удалили — вернуть модель эмбеддингов
  помогает `make warm-embedding`;
* на боевом сервере (`ENVIRONMENT=prod`) сброс заблокирован, пока в `.env`
  не выставлено `ALLOW_DESTRUCTIVE_RESET=true` — предупреждение об этом
  появляется в логах при старте;
* каждый сброс и каждая копия пишутся в **Аудит**: `admin.reset`,
  `admin.backup.create`, `admin.backup.delete`.

После сброса контента документы нужно загрузить заново: индекс PaperQA
строится с нуля (`make reindex` пересобирает его по загруженным файлам).

## 8. Регламент

**Регулярно:**

* `make backup` — ежедневно (cron, пример в OPERATIONS.md);
* `make backup-verify ARCHIVE=...` — еженедельно: архив разворачивается во временный том, проверяются целостность БД и наличие файлов, том удаляется;
* сохранять `SECRET_KEY` из `.env` в хранилище: без него пользователи выйдут за архив без возможности войти;
* обновление Ollama-моделей — при смене `LLM_MODEL`.

**При инциденте:**

1. `docker compose ps` — все ли контейнеры `Up`;
2. `docker compose logs backend | tail -100` — последнее, что произошло;
3. `make health` — состояние БД и Ollama;
4. если данные повреждены — `make down`, затем `make restore ARCHIVE=...` (скрипт попробиует, до очистки сначала страховойка текущего состояния), затем `make up && make health`;

**Решить, «начать с нуля»:** смотрите раздел 7 (вкладка «Сброс») и
`make reset-plan` — сначала план, потом решение, потом бэкап.

**Пользователи жалуются на долгие ответы:** так и должно быть на CPU. Проверьте,
что в `LLM_MODEL` стоит ожидаемая модель, и посмотрите `make metrics` — если
активных задач много, возможно, кто-то грузит большую пачку документов.

## 9. Проверка перед боевым режимом

- [ ] `SECRET_KEY` сгенерирован, не из шаблона
- [ ] `LLM_MODEL` соответствует объёму VRAM боевой машины
- [ ] `ALLOW_EXTERNAL_IMPORT_PATHS=false`
- [ ] `ALLOW_DESTRUCTIVE_RESET=false` (или задокументировано, почему `true`)
- [ ] `OFFLINE_MODE=true`, `MULTIMODAL=false`
- [ ] бэкап снят и **проверен восстановлением**
- [ ] `make health` → `ok`, Ollama доступен
- [ ] администратор создан, тестовый пользователь заведён и проверен
