# Контекст проекта boasi_s

Документ для того, кто продолжает работу: архитектура, статус, ключевые
решения, способы запуска и известные ограничения.

**Платформа:** локальная научная RAG на PaperQA2 + Ollama + FastAPI + Streamlit.
**Код:** <https://github.com/berlogas/bosi_s>
**Планы и отчёты:** [PLAN.md](PLAN.md), [docs/](docs/)

---

## 1. Что это

Исследователь загружает документы (литература, CSV с данными, черновики) и
получает ответы со ссылками на источники, готовит статью по плану разделов и
выгружает её в Word. Ответ занимает минуты — это следствие CPU-инференса, а не
баг.

## 3. Архитектура

```
Streamlit (:8501) ──HTTP──> FastAPI (:8000) ──> SQLite (WAL) на томе boasi_data
                              │
                              ├── Docs (PaperQA) ──> Ollama (:11434)  генерация
                              │                     └── sentence-transformers  эмбеддинги
                              └── document_chunks (чанки + эмбеддинги в SQLite)
```

Две важные особенности:

1. **Индекс PaperQA живёт в памяти процесса.** Персистентность — через
   `document_chunks`: `Text[]` с эмбеддингами в SQLite, восстановление через
   `Docs.aadd_texts` без повторного парсинга и без пересчёта эмбеддингов.
2. **Файловые операции уходят в поток** (`anyio.to_thread`), иначе медленный
   диск встаёт в event loop.

## 4. Ключевые решения

### 4.1 Heartbeat по «арендам», а не по всем активным сессиям

TTL сессии продлевает только реальная активность. Если бы фоновый heartbeat
продлевал TTL всем сессиям со статусом `active`, они **никогда** не истекли бы и
сценарий ТЗ «100 дней без работы → архив» стал бы недостижим.

Клиент с открытой сессией шлёт `POST /sessions/{id}/heartbeat` → ставится
аренда в `app/core/leases.py` (в памяти) → воркер продлевает TTL только по живым
арендам. Побочный эффект в пользу приватности: после рестарта аренды пусты,
«мёртвые» сессии не воскресают.

### 4.2 Один вызов генерации на объединённый контекст

`Docs.aquery(PQASession)` при непустых `contexts` **не вызывает** `aget_evidence`
повторно. Поэтому fusion собирает контекст сам и передаёт готовый.

Инвариант Фазы 0: повторный вызов стоил 374 с против 118 с на CPU. Это
закреплено тестом `test_ready_context_skips_second_search` — он считает вызовы
и требует ровно **2** (по одному на коллекцию).

### 4.3 Один `Docs` на сессию, а не разбивка по категориям

План предполагал разбить сессионную коллекцию по категориям. Оставили одну
коллекцию на сессию (так её строит и восстанавливает Фаза 2/5), а категорию
взвешивают на rerank по `dockey` из реестра. Причина: разбиение означало бы
6 вызовов `aget_evidence` вместо двух — кратный рост времени ответа на CPU.

### 4.4 Приоритет — множитель, а не абсолютный порядок

`final_score = score × priority + бонусы − штраф`. Глобальный источник с
`score=100 × 0.4 = 40` честно обгоняет сессионный `10 × 0.8 = 8`. При равном
score приоритет решает. Ранжирование полностью детерминировано: ключ сортировки
`(-final_score, dockey, name, текст)`.

### 4.5 Числа для модели считает код, не LLM

Для сверки данных с литературой `data_extract.py` читает CSV/TSV (включая
русский разделитель `;` и запятую как десятичную) и отдаёт `n/min/max/среднее`.
Мыслящая машина не пересчитывает и не выдумывает числа: в отчёте о результатах
появились бы выдуманные цифры.

### 4.6 Пробелы в черновике ищутся правилами

Поиск пробелов детерминирован (обязательный раздел без текста, утверждение с
числом или силовым словом без `[n]`, результаты без методики) — иначе результат
нельзя проверить тестом. Модель лишь комментирует найденное.

### 4.7 Своя нумерация цитат

Для генерации разделов промпт собирается самостоятельно (`build_prompt`), а не
через `aquery`: у PaperQA своя нумерация источников и его промпт не гарантирует
контракт ТЗ («каждая цифра `[n]` разрешается в источник»). Проверяется
`validate_citations()` до сохранения версии.

### 4.8 Каталог сессии — своя изоляция

Файлы сессии лежат в `data/sessions/<id>/`. Удаление сессии чистит ровно её
файлы и не задевает чужие. Импорт документа ограничен каталогом сессии, общим
каталогом документов или каталогом данных (`app/core/safety.py`).

## 5. Запуск

**Основной путь — скрипт `scripts/start.sh`, он не требует `make`
(на этой машине `make` не установлен):**

```bash
./scripts/start.sh          # запустить backend + интерфейс
./scripts/start.sh status   # состояние
./scripts/start.sh stop     # остановить
./scripts/start.sh admin ivanov   # создать администратора
```

Пошаговая инструкция — [docs/LAUNCH.md](docs/LAUNCH.md).

### Docker

```bash
cp .env.example .env
python -c "import secrets; print(secrets.token_urlsafe(48))"   # в SECRET_KEY
./scripts/start.sh docker     # тянет модели, собирает образы, поднимает стек
```

### Вручную (три процесса)

```bash
ollama serve                                              # если не запущена
cd backend && ../.venv/Scripts/python.exe -m uvicorn app.main:app --port 8000
cd frontend && ../.venv/Scripts/python.exe -m streamlit run app.py
```

Различия: данные в `data/` вместо тома, `OLLAMA_BASE_URL=http://localhost:11434`.
Бэкап-скрипты работают с томом — в ручном режиме копируйте `data/` напрямую.

## 6. Работа с кодом

```bash
cd backend
../.venv/Scripts/python.exe -m pytest -q      # 388 тестов, ~12 минут
../.venv/Scripts/python.exe -m ruff check app tests
../.venv/Scripts/python.exe -m alembic upgrade head
```

Тесты не ходят в сеть: LLM подменяется заглушкой (`StubLLMModel`), эмбеддинги
локальные. Интеграционные тесты с живым Ollama: `pytest -m integration`.

Полный прогон занимает ~12 минут — не запускайте его на каждый чих, точечный
запуск быстрее: `pytest tests/test_rag_fusion.py -q`.

## 7. Настройки, которые меняют поведение

| Переменная | Смысл |
| --- | --- |
| `LLM_MODEL` | единственный параметр смены модели; скорость не оптимизируется |
| `SECRET_KEY` | обязателен: короткий или шаблонный — приложение не стартует |
| `SESSION_TTL_DAYS` (90) | срок жизни сессии |
| `ARCHIVE_RETENTION_DAYS` (30) | сколько живёт архив до purge |
| `ALLOW_EXTERNAL_IMPORT_PATHS` | расширяет импорт до каталога данных (не за него) |
| `LOGIN_MAX_ATTEMPTS` (10) | порог блокировки логина |
| `EVIDENCE_K` (10) / `ANSWER_MAX_SOURCES` (5) | качество, не скорость |

В коде **нет ни одной константы**, завязанной на скорость: смена модели в бою —
только значение в `.env`.

## 8. Известные ограничения

**Архитектурные (осознанные, по ТЗ — локальный однопользовательский контур):**

* одна реплика backend: реестр задач, аренды и rate-limit живут в памяти;
* SQLite + WAL рассчитан на один процесс записи;
* реестр фоновых задач теряется при рестарте (задачи ставятся заново);
* нет автообновления панели задач в UI — нужен клик «Обновить».

**Недоделанное:**

* Фаза 10 (приёмка по сценарию, регрессионные e2e, `DECISIONS.md`) не начата;
* не проверен рендер UI на 1366×768 (нужен браузер) — ширина ограничена в
  `frontend/app.py`, но фактическую вёрстку не смотрели;
* `docker compose up` и восстановление из бэкапа проверены только статически:
  Docker-демон в среде разработки был недоступен;
* UI-тесты лежат в `backend/tests/test_frontend.py` (чтобы работал общий
  `pytest`); при отделении фронтенда переедут;
* drag&drop проверен только наличием загрузчика — `UploadedFile` через
  `AppTest` не эмулируется;
* нет сохранения шаблонов отчётов в БД (передаются в запросе);
* типы колонок CSV определяются автоматически, задать категориальную нельзя.

## 9. Полезно знать перед правками

* **Единый LLM.** `PaperQA2Service.complete()` — единственная точка вызова
  модели. Если обойти её и построить LLM из настроек, сломается подмена модели в
  тестах (так уже было в Фазе 7).
* **Порядок с `created_at` ненадёжен.** В SQLite метки совпадают в пределах
  микросекунды; при равных метках порядок задаётся добавленным монотонным
  счётчиком (`rowid` для сообщений, `seq` для задач). Не возвращайте сортировку
  только по времени.
* **AppTest ищет по `key`, а не по label.** Позиционный аргумент `at.button(...)`
  — это key; `disabled` пересчитывается только на следующем `run()`.
* **Линтер не пропускает мусор:** ANN, ASYNC240, SIM113 — ruff их проверяет,
  список не полный, но привыкайте чинить сразу.
* **Ловушка bash в `set -u`:** `local name="$1" file="$DIR/$name.pid"` одной
  строкой убивает скрипт — bash раскрывает все слова до присваиваний, `$name`
  считается неприсвоенной, `set -u` завершает процесс, а сообщение об ошибке
  уходит в stderr, который скрипт часто перенаправляет в `/dev/null`. Симптом:
  скрипт молча обрывается без ошибки. Всегда разделяйте `local` на отдельные
  строки.
* **В Windows три `bash.exe`:** Git Bash (`C:\Program Files\Git\...`),
  WSL (`C:\Windows\System32ash.exe`) и заглушка Store
  (`...\WindowsAppsash.exe`). `where bash` отдаёт их в порядке зависимости
  от PATH, и WSL-овский может оказаться первым — тогда `start.bat` падал с
  `execvpe(/bin/bash) failed`. Поэтому `.bat` ищет Git Bash по известным
  путям, отбрасывает WSL/WindowsApps и проверяет найденное запуском
  `bash --version`.
* **Ошибка молчит, если глушить stderr.** Парсинг JSON в `start.sh status`
  сначала падал из-за обратных слэшей в f-string (Python 3.11 их не допускает
  внутри выражения) — и это выглядело как «Backend отвечает, данных нет».
  Ошибки парсинга выводятся явно, а не отбрасываются.
* **Подача эмбеддингов из БД.** В `restore_state` не обнуляйте
  `text.embedding`: пересчёт эмбеддингов после рестарта убивает главное
  преимущество персистентности.

## 10. Куда смотреть при проблемах

| Симптом | Где смотреть |
| --- | --- |
| долгий ответ | `make metrics`, логи `boasi.services.rag` |
| индексация падает | `app/api/documents.py` → `failed` в ответе; логи `add_file` |
| пустой индекс после рестарта | `document_chunks` в SQLite, логи `restore_state` |
| ответы без источников | `app/services/generation.py` → `validate_citations` |
| сессия архивировалась раньше срока | `expire_due_sessions`, реaper в логах |
| 429 на логине | `login_max_attempts` в `.env` |

Логи — JSON в stdout, фильтр: `docker compose logs backend | grep '"ERROR"'`.
