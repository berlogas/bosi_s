# Контекст проекта boasi_s

Документ для того, кто продолжает работу: архитектура, статус, ключевые
решения, способы запуска и известные ограничения.

**Платформа:** локальная научная RAG на PaperQA2 + Ollama + FastAPI + React (`webapp/`).
**Код:** <https://github.com/berlogas/bosi_s>
**Планы и отчёты:** [PLAN.md](PLAN.md), [docs/](docs/)

---

## 1. Что это

Исследователь загружает документы (литература, CSV с данными, черновики) и
получает ответы со ссылками на источники, готовит статью по плану разделов и
выгружает её в Word. Ответ занимает минуты — это следствие CPU-инференса, а не
баг.

## 3. Архитектура

```
React (webapp/, :5173) ──vite-proxy──> FastAPI (:8000) ──> SQLite (WAL) на томе boasi_data
                              │
                              ├── Docs (PaperQA) ──> Ollama (:11434)  генерация
                              │                     └── sentence-transformers  эмбеддинги
                              └── document_chunks (чанки + эмбеддинги в SQLite)
```

Три важные особенности:

1. **Индекс PaperQA живёт в памяти процесса.** Персистентность — через
   `document_chunks`: `Text[]` с эмбеддингами в SQLite, восстановление через
   `Docs.aadd_texts` без повторного парсинга и без пересчёта эмбеддингов.
2. **Файловые операции уходят в поток** (`anyio.to_thread`), иначе медленный
   диск встаёт в event loop.
3. **LLM не обязана быть локальной.** Задан `LLM_API_BASE` (OpenAI-совместимый
   endpoint) — работает облачная модель вместо Ollama
   (`Settings.resolved_llm_api_base`, `api/health.py` не считает недоступный
   Ollama ошибкой в облачном режиме). Эмбеддинги при этом локальные.

## 4. Ключевые решения

### 4.1 Heartbeat по «арендам», а не по всем активным сессиям

TTL сессии продлевает только реальная активность. Если бы фоновый heartbeat
продлевал TTL всем сессиям со статусом `active`, они **никогда** не истекли бы и
сценарий ТЗ «сессия без работы → архив» стал бы недостижим.

Фактический порог — `session_ttl_days = 90` (`app/config.py`), архив снимается
через `archive_retention_days = 30`. В ТЗ фигурировали 100 дней; реализация
сознательно взяла меньший срок (счёт идёт от последнего действия, а не от
последнего открытия), и в документации для пользователя тоже 90.

Клиент с открытой сессией шлёт `POST /sessions/{id}/heartbeat` → ставится
аренда в `app/core/leases.py` (в памяти) → воркер продлевает TTL только по живым
арендам. Побочный эффект в пользу приватности: после рестарта аренды пусты,
«мёртвые» сессии не воскресают.

### 4.1a Живой прогресс: поллинг, а не SSE

При переезде на React планировалось заменить опрос задач на SSE-канал. Не
реализовано: панель задач обновляется через `refetchInterval` раз в 2 с и
гасит опрос, как только активных задач не остаётся
(`webapp/src/features/dashboard/queries.ts`). Для локальной установки это
приемлемо, но лишний запрос на каждый опрос; если захочется
настоящего живого прогресса, начинать надо с SSE на бэкенде и подписки вместо
поллинга.

### 4.2 Один вызов генерации на объединённый контекст

`Docs.aquery(PQASession)` при непустых `contexts` **не вызывает** `aget_evidence`
повторно. Поэтому fusion собирает контекст сам и передаёт готовый.

Инвариант Фазы 0: повторный вызов стоил 374 с против 118 с на CPU. Это
закреплено тестом `test_ready_context_skips_second_search` — он считает вызовы
и требует ровно **2** (по одному на коллекцию).

### 4.3 Один `Docs` на сессию, а не разбивка по категориям

План предполагал разбить сессионную коллекцию по категориям. Оставили одну
коллекцию на сессию (так её строит и восстанавливает Фаза 2/5), а категорию
взвешивают на rerank по `dockey` из реестра. Причина: разбиение означало бы
6 вызовов `aget_evidence` вместо двух — кратный рост времени ответа на CPU.

### 4.4 Приоритет — множитель, а не абсолютный порядок

`final_score = score × priority + бонусы − штраф`. Глобальный источник с
`score=100 × 0.4 = 40` честно обгоняет сессионный `10 × 0.8 = 8`. При равном
score приоритет решает. Ранжирование полностью детерминировано: ключ сортировки
`(-final_score, dockey, name, текст)`.

### 4.5 Числа для модели считает код, не LLM

Для сверки данных с литературой `data_extract.py` читает CSV/TSV (включая
русский разделитель `;` и запятую как десятичную) и отдаёт `n/min/max/среднее`.
Мыслящая машина не пересчитывает и не выдумывает числа: в отчёте о результатах
появились бы выдуманные цифры.

### 4.6 Пробелы в черновике ищутся правилами

Поиск пробелов детерминирован (обязательный раздел без текста, утверждение с
числом или силовым словом без `[n]`, результаты без методики) — иначе результат
нельзя проверить тестом. Модель лишь комментирует найденное.

### 4.7 Своя нумерация цитат

Для генерации разделов промпт собирается самостоятельно (`build_prompt`), а не
через `aquery`: у PaperQA своя нумерация источников и его промпт не гарантирует
контракт ТЗ («каждая цифра `[n]` разрешается в источник»). Проверяется
`validate_citations()` до сохранения версии.

### 4.8 Нумерация правится в тексте, а не только в списке

Номер `[n]` в разделе выдаёт та генерация, которая писала этот раздел, и
раздел за разделом они не совпадают. `plan_citations()` сопоставляет раздел
с версией по тексту (при ручной правке — по последней версии этого раздела),
собирает сквозной порядок по `dockey` и **переписывает маркеры в тексте**
(`rewrite_citations`). Иначе на демо-прогоне Discussion ссылался на `[6]`,
которого в списке из пяти записей не было: список перенумеровывался, текст —
нет.

Диапазон вроде `[3]–[5]` сливается до разбора (`_normalize_bracketed_ranges`),
иначе перенумерация даёт «[5]–[4]». Ссылки без источника не выбрасываются,
а попадают в список строкой «источник не определён» — дыра должна быть видна.

### 4.9 Каталог сессии — своя изоляция

Файлы сессии лежат в `data/sessions/<id>/`. Удаление сессии чистит ровно её
файлы и не задевает чужие. Импорт документа ограничен каталогом сессии, общим
каталогом документов или каталогом данных (`app/core/safety.py`).

## 8. Известные ограничения

**Архитектурные (осознанные, по ТЗ — локальный однопользовательский контур):**

* одна реплика backend: реестр задач, аренды и rate-limit живут в памяти;
* SQLite + WAL рассчитан на один процесс записи;
* реестр фоновых задач теряется при рестарте (задачи ставятся заново).

**Недоделанное:**

* Фаза 10 (приёмка по сценарию, регрессионные e2e, `DECISIONS.md`) не начата;
* рендер вкладки «Проекты» проверен в Chromium на 1366×768: подписи
  двуязычные, ширины полей хватает. Остальные вкладки на этом разрешении
  не смотрели — пункт 8.1;
* четыре падения e2e — `phase3.spec.ts` (редактор проекта) и три в
  `phase4.spec.ts` (создание пользователя, глобальная база, вкладки задач) —
  существовали до двуязычных подписей и на этом проходе не чинились;
* `docker compose up` и восстановление из бэкапа проверены только статически:
  Docker-демон в среде разработки был недоступен (разбор — пункт 8.1);
* drag&drop покрыт тестами: `webapp/src/features/documents/documents.test.tsx`
  (jsdom, `dataTransfer`) и `webapp/e2e/phase3.spec.ts` (через `input[type=file]`);
* нет сохранения шаблонов отчётов в БД (передаются в запросе);
* вид `discussion` требует заполненных разделов: промпт обсуждения
  получает уже написанное (`analyses.written_sections`). Пока Methods и
  Results пусты, обсуждение писать не о чем — порядок генерации важен;
* категория документа задаётся формой при загрузке, поэтому файл с
  другой категорией грузить надо отдельным запросом; смена категории
  постфактум возможна через `PATCH /documents/{id}`;
* `project_focus` (он же автоматический режим при статусе проекта
  `drafting`/`reviewing`) не видит временную литературу: только черновики и
  данные. Для генерации разделов, которым нужны источники, проект должен
  быть в статусе `planning` — тогда работает `hybrid`.
* типы колонок CSV определяются автоматически, задать категориальную нельзя.

### 8.1 Что не проверено — спросить на боевой машине

Ниже то, что **никем не подтверждено на живой машине**: в среде разработки не было
Docker-демона, поэтому часть DoD закрывалась статически.
Пункты переехали сюда из отчётов по фазам; сами отчёты
удалены как дубликаты кода и `PROJECT_CONTEXT`.

| Что | Как проверить |
| --- | --- |
| `docker compose up` с нуля на чистой машине | `make pull-models && make up && make health` |
| Восстановление из бакапа целиком | `make backup && make down && make restore ARCHIVE=... && make up && make health` |
| Сквозной сценарий: две-три подряд подряд, рестарт со снапом сохранения | сценарий из `docs/DEMO_ARTICLE.md` |
| Интеграция с живым Ollama | `pytest -m integration` (по умолчанию пропускается) и `backend/scripts/eval_grounding.py` |
| Вёрстка вкладок на 1366×768 без горизонтального скролла | вручную в Chromium; проверена только вкладка «Проекты» |
| Эталон качества ответов | `backend/scripts/eval_grounding.py` на живой модели; последний прогон делался на `qwen2.5:3b` |
| Четыре падения e2e | `npx playwright test` — падают и сейчас, см. выше |

Полностью оффлайн-контур требует `make warm-embedding`:
без него модель эмбеддингов тянется с HuggingFace при первом старте.

## 9. Полезно знать перед правками

* **Единый LLM.** `PaperQA2Service.complete()` — единственная точка вызова
  модели. Если обойти её и построить LLM из настроек, сломается подмена модели в
  тестах (так уже было в Фазе 7).
* **Порядок с `created_at` ненадёжен.** В SQLite метки совпадают в пределах
  микросекунды; при равных метках порядок задаётся добавленным монотонным
  счётчиком (`rowid` для сообщений, `seq` для задач). Не возвращайте сортировку
  только по времени.
* **В тестах ищи элемент по роли и имени, а не по классу.** В vitest это
  `screen.getByRole('button', { name: /Загрузить файлы/ })`; у Mantine
  `Switch` доступная роль — `switch`, у прогресс-бара текст живёт в
  `aria-label`, поэтому `getByText('40%')` не сработает.
* **У Mantine `Select` имя доступного элемента — «Подпись: значение», а
  варианты лежат в `[role="listbox"]`.** На странице проектов шесть таких
  полей подряд («Проект», «Статус», «Выгрузка статьи», «Вид», «Привязать
  документ», «Роль»), поэтому поиск по индексу или по голой подписи
  открывает не то поле. Ищи по `label[for=<input.id>]` — готовый приём
  есть в `admin.test.tsx:selectOption`.
* **Линтер не пропускает мусор:** ANN, ASYNC240, SIM113 — ruff их проверяет,
  список не полный, но привыкайте чинить сразу.
* **Ловушка bash в `set -u`:** `local name="$1" file="$DIR/$name.pid"` одной
  строкой убивает скрипт — bash раскрывает все слова до присваиваний, `$name`
  считается неприсвоенной, `set -u` завершает процесс, а сообщение об ошибке
  уходит в stderr, который скрипт часто перенаправляет в `/dev/null`. Симптом:
  скрипт молча обрывается без ошибки. Всегда разделяйте `local` на отдельные
  строки.
* **В Windows три `bash.exe`:** Git Bash (`C:\Program Files\Git\...`),
  WSL (`C:\Windows\System32ash.exe`) и заглушка Store
  (`...\WindowsAppsash.exe`). `where bash` отдаёт их в порядке зависимости
  от PATH, и WSL-овский может оказаться первым — тогда `start.bat` падал с
  `execvpe(/bin/bash) failed`. Поэтому `.bat` ищет Git Bash по известным
  путям, отбрасывает WSL/WindowsApps и проверяет найденное запуском
  `bash --version`.
* **Проверяй имена полей моделей глазами.** В `list_audit` стояло
  `AuditLog.ts`, а колонка называется `created_at` — вкладка «Аудит» молча
  отдавала 500 годами: маршрут не вызывали в тестах. Ловится простым
  AST-сканером по обращениям вида `Model.<field>`; такие сканеры стоит
  гонять после правок моделей.
* **Фичевые тесты подменяют API заглушкой — реальный клиент проверяется
  отдельно.** Так в код прокралась ошибка: `raise ApiError(*self._explain(response))`
  распаковывал тройку позиционно, хотя `status` и `detail` объявлены
  keyword-only. Любой ответ 4xx/5xx ронял интерфейс с `TypeError` вместо
  сообщения — то есть неверный пароль показывался аварийно. Теперь есть
  `webapp/src/api/client.test.ts`: разбор ошибок, лимиты, refresh-очередь, 401,
  не-JSON ответ, недоступный backend, заголовок авторизации. Новый код на
  границе с HTTP стоит проверять через настоящий клиент.
* **Ошибка молчит, если глушить stderr.** Парсинг JSON в `start.sh status`
  сначала падал из-за обратных слэшей в f-string (Python 3.11 их не допускает
  внутри выражения) — и это выглядело как «Backend отвечает, данных нет».
  Ошибки парсинга выводятся явно, а не отбрасываются.
* **Подача эмбеддингов из БД.** В `restore_state` не обнуляйте
  `text.embedding`: пересчёт эмбеддингов после рестарта убивает главное
  преимущество персистентности.

* **`lmi` требует pydantic-сообщения, а не dict.** Внутри LLM зовётся
  `m.model_dump()` — на словаре это `AttributeError`, и вся генерация
  падает с 503. В `rag_service.py` это учтено, в `complete()` правило
  забыли: там нужен `Message(content=prompt)` из `aviary.core`.
  `Message.create_message()` у aviary сломан для текста (передаёт
  `content` дважды) — конструктор работает.
* **Нумерация `[n]` локальна для генерации.** Контекст набирается под
  конкретный раздел, поэтому один документ в разных разделах получает
  разные номера. Сквозная нумерация по `dockey` собирается только при
  выгрузке (`collect_references`); в тексте разделов она не перенумеровывается.
* **Пустой ответ от LLM записывается как пустой раздел.** `validate_citations`
  честно ставит `citations_ok: false`, но текст в версию попадает.
  Читайте `word_count` в истории версий: ноль слов — генерация не удалась.
* **Библиография в стиле PaperQA2 — это BibTeX.** Каноническая форма
  (`DocDetails.populate_bibtex_key_citation`), стиль рендера —
  `paperqa.utils.format_bibtex` (`unsrtalpha`), список — как в
  `PQASession.populate_formatted_answers_and_bib_from_raw_answer`:
  только процитированные, в порядке первого появления. Метаданные
  приложение берёт из блока `## Источник` в начале файла; чего там нет,
  в `.bib` не достраивается намеренно.

## 10. Куда смотреть при проблемах

| Симптом | Где смотреть |
| --- | --- |
| долгий ответ | `make metrics`, логи `boasi.services.rag` |
| индексация падает | `app/api/documents.py` → `failed` в ответе; логи `add_file` |
| пустой индекс после рестарта | `document_chunks` в SQLite, логи `restore_state` |
| ответы без источников | `app/services/generation.py` → `validate_citations` |
| сессия архивировалась раньше срока | `expire_due_sessions`, реaper в логах |
| 429 на логине | `login_max_attempts` в `.env` |

Логи — JSON в stdout, фильтр: `docker compose logs backend | grep '"ERROR"'`.
