# Администратору boasi_s

Как завести пользователей, наполнить глобальную базу и следить за системой.
Развёртывание — в [OPERATIONS.md](OPERATIONS.md).

## 1. Первый вход

Регистрации в интерфейсе нет — это осознанно: учётные записи создаёт
администратор. Первого админа создаём из командной строки:

```bash
# В Docker-режиме (start-docker.bat / docker compose):
docker compose exec backend python scripts/create_admin.py <логин>
# Логин: admin
# Пароль: не короче 8 символов

# В классическом запуске без Docker (если есть Makefile):
# make create-admin
```

Войдите на <http://127.0.0.1:5173> → вкладка «Администрирование».

Порт интерфейса задаётся переменной `WEBAPP_PORT` (по умолчанию 5173). Если он
занят, скрипт не занимает соседний порт, а останавливается с ошибкой — освободите
порт или запустите с другим: `WEBAPP_PORT=8600 ./scripts/start.sh`. В Docker
веб-интерфейс поднимается compose вместе с backend и Ollama (см. раздел 10).

## 2. Пользователи

Вкладка **Пользователи** → «Создать пользователя».

| Роль | Что может |
| --- | --- |
| `researcher` | свои сессии, документы, проекты, чат |
| `admin` | всё выше + глобальная база, все сессии, аудит, управление пользователями |

Действия с существующим пользователем (все поля — в одной строке, пустое
«Новый пароль» означает «пароль не меняется»):

* правка **логина** и **ФИО** — прямо в строке, «Сохранить»;
* смена роли — выпадающий список + «Сохранить»;
* смена пароля — поле «Новый пароль»;
* блокировка — переключатель «Активен» (`PATCH` с `is_active=false`).

Про логин: занятый логин нельзя (409, «Пользователь „x“ уже существует»),
минимум 2 символа. Смена логина сразу меняет имя, под которым пользователь
входит. Отметка «Сохранено» появляется поверх таблицы на 2 секунды и не
сдвигает поля.

Удаление пользователя — кнопка «Удалить» в его строке. Подтверждение
предупреждает, что вместе с учётной записью каскадно удаляются его сессии,
сообщения, документы и проекты, и отменить это нельзя. Снять галочку
активности вместо удаления — обратимо, поэтому для «закрыть доступ» она и
предпочтительнее. Перед удалением имеет смысл сделать `make backup`.

Себя удалить нельзя: кнопка у собственной строки задизейблена, а API вернёт 409.

### Команды администратора

Остальные операции с учётными записями — из командной строки (в интерфейсе
их нет намеренно: экран входа показывает исследователю только «обратитесь
к администратору»):

```bash
# Windows
scripts\start.bat admin <логин>
scripts\start.bat password <логин>
scripts\start.bat users

# bash / Linux
./scripts/start.sh admin <логин>
./scripts/start.sh password <логин>
./scripts/start.sh users
```

| Команда | Что делает |
| --- | --- |
| `admin <логин>` | создаёт пользователя с ролью `admin` |
| `password <логин>` | восстанавливает пароль по логину |
| `users` | печатает список пользователей и их ролей |

Вкладки админки живут в адресе: `/admin/users`, `/admin/base`,
`/admin/tasks`, `/admin/sessions`, `/admin/audit`, `/admin/service` — F5
оставляет открытой ту же вкладку, ссылку можно отправить коллеге.

## 3. Глобальная база знаний

Вкладка **Глобальная база**. Здесь документы, доступные **всем** исследователям
(руководства, справочники, общая литература).

Три способа добавить:

1. **Один файл** — путь на диске. Путь должен быть внутри каталога данных
   (например `/data/documents/...`); при желании расширить —
   `ALLOW_EXTERNAL_IMPORT_PATHS=true`.
2. **Загрузка** — перетащите файлы в браузере.
3. **Массовое добавление** — папка-приёмник (см. ниже).

> Индексация одного PDF занимает от секунд до нескольких минут (на dev-машине
> это норма — скорость не оптимизируется). Плата: эмбеддинги считаются локально,
> запрос к LLM на этапе добавления не делается.

Переиндексация (после смены модели эмбеддингов или повреждения кэша):
кнопка «Переиндексировать всё». Долгая операция — не закрывайте вкладку.

Удаление документа убирает его и из индекса, и из реестра — ответы перестанут
на него ссылаться.

### 3.0. Чат отвечает: «база пуста»

Если чат отвечает, что база пуста, а в ответе — «Сейчас база пуста, загрузите материалы» или «контекст упомянутых фрагментов не касается», — это не документы в базе, а индекс: тексты лежат в БД, но поиск по ним не идёт.

**Как проверить.** В логах backend ищите строку:

```
restore_state: коллекция=global восстановлено=0 чанков=0 устарело=17
```

Значит, индекс не восстановился: чанки лежат в БД, но признаны непригодными и пропущены. Нормальное состояние — когда устаревших нет:

```
restore_state: коллекция=global восстановлено=17 чанков=51 устарело=0 легаси=0
```

**Почему чанки устаревают.** Чанк — это текст документа и его вектор. Он зависит от модели эмбеддингов и от нарезки на фрагменты, но не от модели, которая пишет ответ. Поэтому смена LLM (например, переход с облака на локальный Ollama) индекс НЕ обесценивает: переиндексация не нужна, меняются только формулировки ответа, а состав источников остаётся прежним.

Обесценивают индекс: смена модели эмбеддингов, смена размера чанка, повреждение кэша. Отпечаток специально считается только по значимым полям (модель эмбеддингов и нарезка) — без абсолютных путей и без ключа API, иначе одна и та же база, открытая с хоста и из контейнера, считала бы чанки устаревшими.

**После обновления системы база не должна «исчезать».** В `settings_md5` чанка пишется отпечаток с префиксом версии (`v2:`). Записи без префикса — легаси: в них лежал старый, более широкий отпечаток (или вовсе dockey). Они восстанавливаются автоматически и сразу пересохраняются с текущим отпечатком; в логе это строка с `легаси=N`:

```
restore_state: коллекция=global восстановлено=17 чанков=51 устарело=0 легаси=8
```

Такие записи переиндексации не требуют. Если же в логе `устарело>0` и `легаси=0` — это настоящая смена модели эмбеддингов или нарезки, и нужна переиндексация.

**Что делать, если устарело.** Переиндексация: пересчитать эмбеддинги и перезаписать отпечаток.

```bash
# В контейнере:
docker compose exec backend python scripts/reindex.py
```

Скрипт пересчитывает эмбеддинги, обновляет отпечаток и сохраняет индекс. На машине разработчика занимает около минуты (17 документов).

### 3.0.1. Чат долго не отвечает («Вопрос обрабатывается…» без конца)

На слабом железе (Ollama на CPU) поиск по базе — это не только эмбеддинги: при `EVIDENCE_SKIP_SUMMARY=false` PaperQA делает **отдельный вызов LLM на каждый фрагмент выдачи** (`EVIDENCE_K` штук) и только потом пишет ответ. Один такой вызов на CPU идёт минуты, поэтому до ответа могли проходить десятки минут.

Теперь ожидание сводок ограничено `EVIDENCE_SUMMARY_TIMEOUT_SECONDS` (по умолчанию 120 с). Если сводки не уложились, поиск автоматически повторяется без них — релевантность считается по эмбеддингам, и ответ приходит. В логе это видно так:

```
fusion: сводки не уложились в 120.0с — поиск без них
```

Что подкрутить, если всё равно долго:

- `EVIDENCE_K` — число фрагментов, а значит и число вызовов LLM (5 на CPU, 10 на GPU);
- `EVIDENCE_SUMMARY_TIMEOUT_SECONDS` — уменьшить (например, 60) или поставить `0`, чтобы ждать без предела;
- `EVIDENCE_SKIP_SUMMARY=true` — вообще не делать сводок (быстрее, но в контекст идёт сырой текст).

Если задача оборвалась из-за перезапуска backend, вопрос больше не исчезает молча: в чате остаётся вопрос и ошибка «не удалось получить состояние задачи». Достаточно отправить его ещё раз.

### 3.1. Массовое добавление через папку-приёмник (inbox)

Основной сценарий для Docker: положить много файлов сразу, без загрузки
каждого через браузер.

1. Кладёте файлы в папку `data/inbox/` в корне репозитория (в контейнере она
   смонтирована как `/data/inbox` — тот же каталог, но размещение общего
   каталога данных). Подпапки не запрещены.
2. В админке → «Глобальная база» → «Запустить массовое добавление».
   Кнопка активна, только когда в папке есть принимаемые файлы.
3. Backend для каждого файла: индексирует, переносит в
   `/data/documents/library/YYYY-MM/`, обновляет путь в БД и только потом
   убирает файл из inbox. Папка приёмника остаётся пустой и готовой к
   следующей порции.

Отчёт — **журнал добавления** под кнопкой, он переживает перезагрузку страницы
и перезапуск контейнера (лежит в БД, а не в логе). По каждому файлу видно
статус и причину, если что-то пошло не так; кнопка «почему?» раскрывает текст:

| Что | Куда | Почему |
| --- | --- | --- |
| принят | `library/YYYY-MM/` | всё прошло |
| заменён | `library/YYYY-MM/` | файл с тем же именем уже был — считается исправленной версией, прежний документ и его файл удалены |
| отклонён | `rejected/<дата>/` | неподдерживаемый тип или больше `UPLOAD_MAX_MB` |
| ошибка | остаётся в inbox | не удалось проиндексировать (битый PDF и т. п.) — причина в тексте |

Прочие свойства:

* автоматического скана по расписанию **нет** — только кнопка; это осознанно,
  так как «проверить rejected» должен оставаться ручным действием;
* прерванный прогон (перезапуск контейнера посреди обработки) помечается
  в журнале как прерванный, временные файлы подчищаются при старте;
* `rejected/` чистится кнопкой «Очистить ошибочные» — причины остаются в
  журнале добавления;
* кнопка «Переиндексировать всё» живёт у списка «Документы глобальной базы»:
  переиндексация — это про уже добавленные документы, а не про приёмник.

### 3.2. Предупреждение «факт не подтверждён источниками»

Под ответом чат может показать жёлтое предупреждение: какое-то утверждение из ответа не нашлось в источниках. Это не поломка, а сигнал: модель добавила деталь, которой нет в загруженных документах.

Предупреждение появляется, когда в ответе есть число, имя или другая «сущность», отсутствующая в исходном тексте найденных документов. Проверка идёт именно по **исходному тексту** документа, а не по пересказу модели: пересказ сделала та же модель, что и ответ, и доверять ему нельзя — выдумка в пересказе выглядела бы как подтверждённый факт.

Что делать:

* **Проверьте источник.** Часто модель права, а документ написан обтекаемо («сушка при 60 °C» против «сушка в течение часа при температуре 60 °C») — тогда в источнике просто ищите точную формулировку.
* **Слабая модель выдумывает детали.** На локальном Ollama 3B это заметно: модель может написать «105 °C», взяв число из соседнего абзаца. Это и есть повод перейти на модель помощнее (см. 10.6.1).
* **Если факт есть, а предупреждение осталось** — сообщите разработчику: правило проверки можно уточнить (например, разрешить числа с единицами измерения).

Предупреждения пишутся в историю ответов (`messages.checks`) — их видно и потом, когда открываете старый диалог. Полный список — в отчёте `stats.grounding`: `checked` (сколько сущностей проверено), `grounded` (сколько подтверждено), `ungrounded` (список неподтверждённых).

## 4. Сессии

Вкладка **Сессии** показывает все сессии всех пользователей, сгруппированные по
владельцам: каждая группа свёрнута в заголовок с именем пользователя и
счётчиком «N сессий», внутри — таблица с колонками «id» (первые 8 символов),
«название», «статус», «действие» и «активность». То же самое на информационной
панели: карточки сессий разложены по владельцам, собственные идут первыми,
поэтому «свои» не теряются в общем списке.

Управление сессиями из UI не предусмотрено (своими исследователь управляет
сам) — это осознанное ограничение, чтобы админ не мог спутать чужую работу.
Посмотреть результат операции можно из вкладки **Задачи**: под каждой задачей
есть ссылки «Открыть сессию», «Открыть проекты» и «Документы (N)».

## 5. Задачи

Вкладка **Задачи** — все фоновые операции: индексация, вопросы по контексту,
генерация разделов. Видны прогресс, текущий шаг и ошибки. Задачу можно
отменить — работа прервётся на ближаетшем шаге.

Ошибки индексации (`DocumentProcessingError`) чаще всего означают
неподдерживаемый тип файла — сверьтесь со списком `ALLOWED_EXTENSIONS` в `.env`.

Доступно:

* фильтры по статусу (все / активные / завершённые / с ошибкой /
  отменённые) и по пользователю, счётчик «показано N из M»;
* под каждой задачей — автор и ссылки «Открыть сессию», «Открыть проекты»
  и «Документы (N)» — переход к результату операции;
* «Очистить завершённые» — убирает из списка завершённые задачи
  (`POST /api/tasks/clear`). Активные задачи не трогаются, действие
  требует подтверждения и необратимо: результат виден только в сессиях
  и документах, в списке задач его больше не будет.

Задачу нельзя «создать» — она появляется сама, когда интерфейс или скрипт
запускает операцию (ответ LLM, индексация, загрузка, переиндексация).
Вкладка админки — только наблюдение и управление ходом.

## 6. Аудит

Вкладка **Аудит** — журнал действий: кто, что, когда, с какого IP.
Доступно:

* фильтр по периоду (всё время / 7 / 30 / 90 дней) — уходит в API как
  `since`, граница считается по началу суток;
* «Выгрузить CSV» — файл с тем же периодом, до 10 000 записей,
  разделитель `;` и BOM (иначе Excel ломает кириллицу);
* сводка «всего записей: N, самые старые от <дата>» — видно, что ретрация
  работает: список-то всегда ограничен одной страницей.

### Как журнал не раздувается

`audit_log` растёт на каждое действие, поэтому у reaper'а есть четвёртая
операция (раз в `AUDIT_PRUNE_INTERVAL_HOURS`, по умолчанию сутки):

| Правило | Параметр | Смысл |
| --- | --- | --- |
| по сроку | `AUDIT_RETENTION_DAYS=180` | старше — вон |
| по объёму | `AUDIT_MAX_ROWS=200000` | при интенсивной работе важнее срока: уходят самые старые до порога |
| защита | `AUDIT_PROTECTED_ACTIONS` | эти действия не выселяются **никогда** |

Защищённые по умолчанию: `admin.user.delete`, `admin.reset`,
`admin.backup.delete`, `admin.documents.clear`, `admin.inbox.rejected.clear`,
`session.delete`, `project.delete` — то есть ответ на вопрос «кто и когда
сбросил или удалил» остаётся и через год. Сравнение по префиксу, поэтому
`admin.reset` прикрывает и будущие `admin.reset.*`.

После удаления SQLite не отдаёт место файлу, поэтому следом выполняется
`VACUUM` (если `AUDIT_VACUUM=true`) — в отдельном соединении с
AUTOCOMMIT, раз в сутки: он блокирует запись на время выполнения.
Значения `0` отключают правило целиком.


## 7. Обслуживание: копии и сброс

Вкладка **Обслуживание** — две операции, которые лучше не искать по разным
местам: снять копию и стереть платформу.

### Резервные копии

Кнопка **Создать копию** — архив с базой данных (согласованный снимок),
файлами сессий и документов, манифестом с ревизией схемы и контрольной
суммой. Платформа не останавливается — снять можно прямо по работе.

Фразы подтверждения не нужно: операция ничего не
разрушает, худшее — потратится место на диске, и объём показан в окне.

Копии складываются в каталог **за пределами данных** (`/backups` в Docker,
`backups/` локально). Иначе копия попадала бы сама в себя и каждый раз
расти без предела.

Автоматическая ротация: хранится `BACKUP_KEEP` копий (по умолчанию — 14),
при создании новой более старые удаляются. Ненужные копии можно удалить
кнопкой в таблице.

Проверить копию, не распаковывая:

```
scripts\boasi.bat backup-verify backups\boasi-20261008-120000.tar.gz   # Windows
./scripts/verify_backup.sh backups/boasi-20261008-120000.tar.gz       # bash
```

Копия из админки содержит снимок базы в том же формате, что у скриптов.
После нажатия появится уведомление в правой верхней части страницы,
а список перечитывается сам — нажимать «Обновить» не нужно.

### Восстановление — только скриптом

Восстановление требует остановки платформы: база в этот момент уже исчезает,
пока идёт распаковка. Поэтому в браузере его нет, а подсказка в разделе
ведёт к скрипту:

```bash
# Windows
scripts\start.bat stop
scripts\boasi.bat restore backups\boasi-20261008-120000.tar.gz
scripts\start.bat

# bash / Linux
./scripts/start.sh stop
./scripts/restore.sh backups/boasi-20261008-120000.tar.gz
./scripts/start.sh
```

Порядок такой, что «восстановил не тот архив» не стоит данных: скрипт
сначала сверяет контрольную сумму, потом кладёт страховочную копию текущего
состояния в `backups/pre-restore/`, и только затем чистит каталог.

### Сброс состояния

Вторая половина вкладки — те же уровни, что и раньше: от «данные» до «всё».
Единственный путь назад — сброс, сделанный **до** него. Снимите копию заранее.

| Уровень | Что удаляется | Что остаётся |
| --- | --- | --- |
| Данные | сессии, документы, проекты, переписка, файлы, индекс | пользователи, аудит |
| Данные и входы | то же + все refresh-токены (всем нужно войти заново) | пользователи, аудит |
| Всё | то же + учётные записи и аудит | ничего, платформа пуста |

Важно:

* сбрасываются и сообщения в чате, и черновики проектов, и загруженные файлы —
  восстановить их можно только из копии;
* **«Также удалить кэш моделей»** обычно трогать не надо: без него платформа
  останется работать в офлайне; если удалили — вернуть модель эмбеддингов
  помогает `make warm-embedding`;
* на боевом сервере (`ENVIRONMENT=prod`) сброс заблокирован, пока в `.env`
  не выставлено `ALLOW_DESTRUCTIVE_RESET=true` — предупреждение об этом
  появляется в логах при старте;
* каждый сброс и каждая копия пишутся в **Аудит**: `admin.reset`,
  `admin.backup.create`, `admin.backup.delete`.

После сброса контента документы нужно загрузить заново: индекс PaperQA
строится с нуля (`make reindex` пересобирает его по загруженным файлам).

## 8. Регламент

**Регулярно:**

* `make backup` — ежедневно (cron, пример в OPERATIONS.md);
* `make backup-verify ARCHIVE=...` — еженедельно: архив разворачивается во временный том, проверяются целостность БД и наличие файлов, том удаляется;
* сохранять `SECRET_KEY` из `.env` в хранилище: без него пользователи выйдут за архив без возможности войти;
* обновление Ollama-моделей — при смене `LLM_MODEL`.

> **Когда чинить `SECRET_KEY` (не срочно, но обязательно перед выкладкой).**
> 2026-11-13 в репозитории найден файл `.envold` с рабочим `SECRET_KEY`.
> Файл удалён из рабочей копии, но он **остался в истории git**
> (коммит `0387f47`).
>
> Пока приложение не эксплуатируется, ключ можно оставить прежним: подделать
> токен по ключу из истории git нельзя, пока к серверу нет доступа извне.
> Но **перед выкладкой** ключ нужно перегенерировать — после этого история git
> перестанет быть слабым местом.
>
> Что сделать перед выкладкой:
>
> 1. Сгенерировать новый ключ: `python -c "import secrets; print(secrets.token_urlsafe(48))"`.
> 2. Положить его в `.env` (`SECRET_KEY=<новое значение>`) — и в то же
>    хранилище, где хранится старый ключ (см. «Регулярно» выше).
> 3. Перезапустить backend: `docker compose restart backend`.
> 4. **Все пользователи разлогиняются** — старые токены, подписанные прежним
>    ключом, перестанут проверяться. Предупредите об этом заранее.
>
> Если репозиторий станет публичным, ключ нужно считать скомпрометированным
> немедленно, независимо от того, удалён ли файл из рабочей копии.

**При инциденте:**

1. `docker compose ps` — все ли контейнеры `Up`;
2. `docker compose logs backend | tail -100` — последнее, что произошло;
3. `make health` — состояние БД и Ollama;
4. если данные повреждены — `make down`, затем `make restore ARCHIVE=...` (скрипт попробиует, до очистки сначала страховойка текущего состояния), затем `make up && make health`;

**Решить, «начать с нуля»:** смотрите раздел 7 (вкладка «Сброс») и
`make reset-plan` — сначала план, потом решение, потом бэкап.

**Пользователи жалуются на долгие ответы:** так и должно быть на CPU. Проверьте,
что в `LLM_MODEL` стоит ожидаемая модель, и посмотрите `make metrics` — если
активных задач много, возможно, кто-то грузит большую пачку документов.

## 10. Работа через Docker: запуск, обновление, бэкапы

Если платформа развёрнута через Docker Compose ( `scripts\start-docker.bat` ),
все операции обслуживания делаются консолью. Краткая шпаргалка ниже.

### 10.1. Запуск и остановка стека

```cmd
scripts\start-docker.bat        # запустить стек (ollama + backend + webapp)
scripts\start-docker.bat stop   # остановить
scripts\start-docker.bat status # состояние контейнеров
scripts\start-docker.bat logs   # логи backend (по умолчанию)
scripts\start-docker.bat logs webapp   # логи интерфейса
```

Доступ после запуска: UI — `http://127.0.0.1:5173`, API — `http://127.0.0.1:8000/api/docs`.

### 10.2. Обновление после правок кода

| Команда | Когда использовать |
|---------|-------------------|
| `scripts\start-docker.bat rebuild` | Пересобрать всё (backend + webapp) |
| `scripts\start-docker.bat rebuild-backend` | Только backend (изменения в `backend/app/`) |
| `scripts\start-docker.bat rebuild-webapp` | Только интерфейс (изменения в `webapp/src/`) |
| `scripts\start-docker.bat restart` | Перезапуск без пересборки (только `.env` / compose) |

После пересборки backend подождите ответа `/api/health` — на первом старте грузится модель эмбеддингов и восстанавливается индекс (минуты, а не секунды).

### 10.3. Бэкап в Docker-режиме

Скрипт `scripts/backup.sh` автоматически определяет режим: если бакенд работает в контейнере — снимок БД делается через снимок SQLite (`sqlite3 .backup`),
не копирование файла. Не нужно указывать дополнительные флаги.

```bash
# Git Bash (из корня проекта)
bash scripts/backup.sh

# Сохранить ещё и .env (с SECRET_KEY) отдельным файлом
CONFIG_BACKUP=1 bash scripts/backup.sh

# Сохранить ещё и модели Ollama (много гигабайт)
MODELS_BACKUP=1 bash scripts/backup.sh

# Оставить только последние 14 архивов
KEEP_BACKUPS=14 bash scripts/backup.sh
```

Архив пишется в `backups/boasi-YYYYmmdd-HHMMSS.tar.gz` рядом с контрольной суммой `*.sha256`.

Посмотреть содержимое архива, не распаковывая:

```bash
bash scripts/restore.sh backups/boasi-YYYYmmdd-HHMMSS.tar.gz --list
```

Проверить архив без последствий:

```bash
bash scripts/verify_backup.sh backups/boasi-YYYYmmdd-HHMMSS.tar.gz
```

### 10.4. Восстановление из бэкапа в Docker

**Важно:** перед восстановлением стек должен быть остановлен, иначе SQLite продолжит писать в удаляемые файлы.

```cmd
:: 1. Остановить стек
scripts\start-docker.bat stop

:: 2. Восстановить (Git Bash, ввести слово ВОССТАНОВИТЬ)
bash scripts/restore.sh backups/boasi-YYYYmmdd-HHMMSS.tar.gz

:: 3. Запустить стек снова (миграции пройдут автоматически)
scripts\start-docker.bat start

:: 4. Проверить статус
scripts\start-docker.bat status
```

Если нужно восстановить не в том же месте, а в другой каталог:

```bash
bash scripts/restore.sh backups/boasi-YYYYmmdd-HHMMSS.tar.gz --target ./data-restored
```

Страховочная копия текущего состояния сохраняется в `backups/pre-restore/` перед чисткой.

### 10.5. Администратор и пользователи в Docker

Создание админа и сброс пароля делаются внутри контейнера backend:

```cmd
docker compose exec backend python scripts/create_admin.py <логин>
docker compose exec backend python scripts/reset_password.py <логин>
docker compose exec backend python scripts/reset_password.py --list
```

### 10.6. Где лежат данные

Данные лежат в каталоге `data/` в корне репозитория. Контейнер видит его как bind-mount (`./data:/data`),
поэтому та же БД и файлы видны и контейнеру, и локальному запуску backend — без копирования БД.

| Каталог на хосте | В контейнере | Содержимое |
|------|--------------|------------|
| `data/` | `/data` | SQLite БД, сессии, документы, индекс, кэш эмбеддингов |
| `data/inbox/` | `/data/inbox` | Папка-приёмник для массового добавления |
| `backups/` | `/backups` | Архивы бэкапов и контрольные копии |
| том `boasi_ollama_models` | `/root/.ollama` | Модели Ollama (единственный том, не под данными) |

Пути файлов в БД хранятся относительно от каталога данных: путь `documents/uploads/x.md` одинаково для хоста и контейнера. Поэтому каталог данных можно перенести с хоста на контейнер без копирования.

Архивы бэкапов пишутся на хост в папке `backups/`, поэтому при `docker compose down -v` они не удаляются.

⚠️ `docker compose down -v` **удаляет том моделей** — бизнес-каталог `data/` останется целиком (БД, документы, сессии). Перед удалением всё равно снимите бэкап.

### 10.6.1. Локальный Ollama на слабой машине

Если LLM работает локально (Ollama на CPU, без GPU), скорость ответа
определяется двумя числами: размером контекста и числом вызовов модели.

**Сколько вызовов делает один вопрос.** Алгоритм PaperQA2 «Собери
доказательства» сначала просит LLM кратко пересказать каждый найденный
фрагмент и переоценить его релевантность, и только потом зовёт модель за
ответом. При `EVIDENCE_SKIP_SUMMARY=false` это один вызов на фрагмент плюс
один на ответ. Фрагментов берётся `_evidence_k()` штук — не меньше
`EVIDENCE_K`, с запасом на rerank.

**Замер на dev-машине** (i7-3770, 4 ядра, `ministral-3:3b` Q4_K_M, Ollama на
CPU): промпт 1310 токенов обрабатывается ~19 токенов/с, то есть ~70 с
только на префилл одного вызова. Отсюда практические правила:

* `EVIDENCE_SKIP_SUMMARY=true` — сводок не делается, модель получает сырой
  текст. Вызовов меньше (обычно один), отвечает быстрее. Релевантность
  считается только по косинусу.
* `EVIDENCE_K=5` (а не 10) — меньше фрагментов, меньше вызовов.
* `MAX_CONCURRENT_REQUESTS=1` — Ollama на CPU обрабатывает запросы
  последовательно; параллельные запросы делят ядра и только растягивают
  очередь. Значение 4 и выше имеет смысл с облачной моделью или с GPU.

В `.env.example` описаны оба режима: «отладочный» (облачная LLM, сводки
включены, качество выше) и «боевой» (Ollama на GPU). Локальный Ollama на
CPU — это третий случай, и для него верны настройки отладочного режима с
`MAX_CONCURRENT_REQUESTS=1`.

На боевом сервере с GPU эти ограничения не нужны: там `EVIDENCE_SKIP_SUMMARY=false`
и `EVIDENCE_K=10` дают качественный ответ за 15–25 секунд.

### 10.7. Развёртый сервер на Linux

Каталог данных — bind-mount на хоста, поэтому без особычности и тома Docker не нужны.

```bash
git clone <репозиторий> /opt/boasi_s
cd /opt/boasi_s
cp .env.example .env
./scripts/bootstrap.sh
```

**Права владельца каталога данных.** Контейнер по умолчанию пишет от роота (`root`), и файлы в `data/` будут принадлежать только от себя. Чтобы этого не произошлось:

```bash
DOCKER_UID=$(id -u) DOCKER_GID=$(id -g) docker compose up -d
```

Это делает владелице каталога чисто вашему узнауста. Запишите это в `.env` или в экране запуска:

```env
DOCKER_UID=1000
DOCKER_GID=1000
```

Если сотраненные файлы уже созданались под root — это работает, но т укаранать станет опция не получится.

Проверьте, что база подшомана: индекс и чанки всего восстановлены в контейнере, а то ут не встанат настоящие заначения и сессии.

### 10.8. Чистая установка на новом сервере

Если на сервере понамааат старам базу — просто очистить каталог `data/` и поднять старую БД:

```bash
cd /opt/boasi_s

# 1. Остановить стек (иначе сбой бы почерку страшки не успели снова после сбоя)
docker compose down

# 2. Очистить БД и файлы
rm -rf data/boasi.sqlite3 data/boasi.sqlite3-wal data/boasi.sqlite3-shm
rm -rf data/documents data/sessions data/pqa data/rejected

# 3. Поднять стек и создать администратора
docker compose up -d
docker compose exec backend python scripts/create_admin.py admin --password "новый-пароль"

# 4. Проверить
docker compose exec backend python scripts/reset_password.py --list
curl -fsS -X POST http://127.0.0.1:8000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"новый-пароль"}'
```

Сбор через администратор всего сначала — так же без предварительного сбоя:

```bash
make reset-all        # полный сброс всего (таблицы, сессии, документы, качек моделей)
```

`reset_state.sh` сам останавливает backend на время сброса и поднимает его снова: работающий backend держит старый handle на БД,
и SQLite не даёт открывать базу с открытым файлом. После сброса скрипт поднимает backend обратно.

⚠️ **Сброс удаляет делает файлы.** Сброс удаляет каталоги с файлами документов. Если убойть нужно, но сначала убедится старый процесс backend — он будет работать с пустым каталогом, а с файлами — по большему времени по данным не вернётся.

### 10.9. Перенос со старой схемы (том `boasi_data`)

Если платформа раньше работала с именованным томом Docker, а теперь — с каталогом `data/`, перенос делается один раз:

```bash
# 1. Остановить стек
docker compose down

# 2. Скопировать данные тома в каталог (том остаётся как страховка)
docker run --rm -v boasi_data:/from:ro -v "$(pwd)/data:/to" alpine \
  sh -c "cp -a /from/. /to/"

# 3. Перевести пути файлов в БД на относительные (относительно DATA_DIR)
python backend/scripts/relocate_paths.py --extra-root /data

# 4. Поднять стек и проверить
docker compose up -d
docker compose exec backend python scripts/reset_password.py --list
```

Шаг 3 обязателен: до него в БД лежали абсолютные пути вида `/data/documents/...`,
которые в контейнере и на хосте указывают на разные файлы — документы «исчезали»,
а экспорт переставал читать файлы. Скрипт идемпотентен и безопасен для повторного
запуска. После перевода том `boasi_data` можно удалить:

```bash
docker volume rm boasi_data
```

Проверить, что пути переведены:

```bash
python -c "import sqlite3;print(sqlite3.connect('data/boasi.sqlite3').execute('select path from documents limit 3').fetchall())"
```

Ожидаемый вид — относительные пути без префикса каталога:

```
[('documents/uploads/x.md',), ...]
```

### 10.10. Перенос разделов в новую модель (`section_plans`)

Текст раздела хранится в двух моделях сразу:

- **старая** — `projects.sections` (JSON) и `project_versions`; её читают прогресс проекта
  и выгрузка (Word / Markdown / ZIP);
- **новая** — `section_plans` + `section_versions`; её читает интерфейс (редактор раздела,
  история версий, панель «История»).

Проекты, написанные до перехода на новую модель, в интерфейсе выглядят пустыми: раздел есть,
текст есть, а плана с этим текстом нет. Переносит текст скрипт:

```bash
# 1. Показать, что перенесётся (ничего не пишет)
python backend/scripts/sync_section_plans.py --dry-run

# 2. Перенести
python backend/scripts/sync_section_plans.py

# 3. Перезапустить backend, если он работал во время прогона
docker compose restart backend
```

Скрипт идемпотентен: у плана, у которого уже есть текущая версия, текст не трогается.
Новые генерации в обе модели пишутся сами — раздел, созданный через интерфейс, сразу
появляется и в выгрузке, и в редакторе.

**Что где лежит (на 2026-11-12).** Источник истины — новая модель:
`section_plans` (план разделов) и `section_versions` (тексты, история, цитаты).
Старая модель — `projects.sections` (JSON) и `project_versions` — осталась зеркалом:
её пишут, но не читают. Прогресс проекта, выгрузка и разбор черновика берут
разделы из планов; пока планов нет (проект до перехода) — из старой модели.

Поэтому `GET /manuscript` ничего не пишет в базу — в отличие от прежнего
поведения, когда просмотр манускрипта создавал планы разделов. Перенос
делается явно: кнопкой «Синхронизировать из JSON» или скриптом выше.
