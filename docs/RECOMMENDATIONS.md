# Рекомендации по улучшению boasi_s

Дата: 2026-10-19

---

## Архитектура и код

### 1. Персистентность индекса PaperQA2 — ключевая сила, но есть риск

Индекс живёт в памяти процесса, персистентность через `document_chunks` в SQLite. Это правильное решение для PaperQA2 (у него нет встроенной персистентности `NumpyVectorStore`).

**Рекомендация:** Добавить версионирование схемы `document_chunks`. Сейчас `settings_fingerprint` гарантирует несовместимость при смене настроек, но нет миграции — при изменении структуры чанков старые записи молча станут нечитаемыми. Добавьте `schema_version` в таблицу и проверку при старте.

### 2. `rag_service.py` — 929 строк, слишком много ответственности

Файл содержит: болтовню, identity-запросы, refusal detection, citation renumbering, header localization, evidence retrieval, answer generation. Это нарушает SRP.

**Рекомендация:** Разбить на модули:
- `rag_trivial.py` — болтовня + identity
- `rag_citations.py` — renumbering + repair
- `rag_retrieval.py` — evidence + merge
- `rag_generation.py` — вызов `aquery` + пост-обработка

### 3. `paperqa_service.py` — 812 строк, аналогичная проблема

**Рекомендация:** Выделить `PaperQA2Persistence` (save/restore в `ChunkStore`) и `PaperQA2Registry` (управление коллекциями) в отдельные модули.

## Соответствие требованиям PaperQA2

### 4. Использование `Docs.aadd_texts()` — правильно

Восстановление индекса из SQLite без повторного парсинга PDF — это то, как PaperQA2 задуман для персистентности. Хорошо.

### 5. `aquery(PQASession)` с готовым контекстом — правильно

Избегаете повторного `aget_evidence` (374с → 118с на CPU). Это документированное поведение PaperQA2.

### 6. RAG Fusion — не стандартный режим PaperQA2

PaperQA2 умеет искать по одной `Docs` коллекции. Ваш fusion (параллельный поиск по глобальной + сессионной, merge + rerank) — это надстройка над API.

**Рекомендация:** Рассмотрите использование нескольких `PQASession` с разными `Docs` и слиянием на уровне ответов, если PaperQA2 добавит нативную поддержку multi-collection. Пока — ваш подход корректен.

### 7. Модель эмбеддингов

Используете `st-multi-qa-MiniLM-L6-cos-v1` вместо Ollama-эмбеддингов. Это правильно для CPU-режима (Ollama даёт 10 мин на PDF и HTTP 400 на русском).

**Рекомендация:** Для prod с GPU рассмотрите `BAAI/bge-m3` — мультиязычный, лучше для русского, поддерживает длинные контексты (8192 токенов).

## Производительность и масштабирование

### 8. Поллинг задач каждые 2 секунды

При большом количестве активных задач это создаёт нагрузку.

**Рекомендация:** Реализуйте SSE (Server-Sent Events) для прогресса задач. FastAPI поддерживает `StreamingResponse` нативно. Это уменьшит нагрузку и даст настоящий real-time прогресс.

### 9. `max_concurrent_requests=1` для LLM

Оправдано для CPU, но при переходе на GPU станет узким местом.

**Рекомендация:** Вынесите в конфиг `LLM_CONCURRENT_REQUESTS` с дефолтом 1, чтобы prod мог масштабироваться без правок кода.

### 10. Отсутствие кэша эмбеддингов на уровне запроса

Каждый вызов `aget_evidence` считает эмбеддинги запроса заново.

**Рекомендация:** Кэшируйте эмбеддинги запросов в LRU-кэше (например, `functools.lru_cache` или Redis для распределённого режима). Повторные запросы с тем же текстом будут мгновенными.

## Безопасность и эксплуатация

### 11. Приватность — соблюдается

Никаких внешних вызовов во время работы, ключи Crossref/Semantic Scholar не используются. Это соответствует требованиям PaperQA2 для локального развёртывания.

### 12. Аудит чтения глобальной базы отсутствует

`GET /api/documents` не пишет в аудит. Это осознанное решение (иначе страница засоряет журнал), но для compliance может быть проблемой.

**Рекомендация:** Добавить опциональный аудит чтения с флагом `AUDIT_READS=true` для режима аудита.

### 13. Нет rate limiting на загрузку документов

`POST /api/documents/upload` не ограничен по частоте.

**Рекомендация:** Добавить rate limit на загрузку (например, 10 файлов/минуту) через существующий `app/core/rate_limit.py`.

## Тестирование

### 14. 690 тестов — хорошо, но нет coverage

**Рекомендация:** Добавьте `pytest-cov` и отчёт о покрытии. Цель — 80%+ для `services/` и `api/`.

### 15. Нет интеграционных тестов с реальным Ollama

2 deselected теста — интеграционные с живым Ollama.

**Рекомендация:** Добавьте пометку `@pytest.mark.integration` и запускайте их отдельно в CI с поднятым Ollama-контейнером.

### 16. E2E-тесты Playwright — 7 сценариев

Для приёмки по сценарию (Фаза 10) этого может быть недостаточно.

**Рекомендация:** Добавьте сценарии для: загрузки документа → поиска → генерации раздела → экспорта в Word. Это основной пользовательский путь.

## Документация

### 17. Документация отличная, но нет API reference для разработчиков

`docs/` содержит руководства для пользователя и администратора, но нет справочника по API для разработчиков.

**Рекомендация:** Добавьте `docs/API_REFERENCE.md` с примерами запросов/ответов для ключевых эндпоинтов.

### 18. Нет changelog

**Рекомендация:** Добавьте `CHANGELOG.md` с версионированием (SemVer). Это важно для отслеживания изменений между фазами.

## Фронтенд

### 19. `webapp/src/api/schema.ts` — 159 KB

Это сгенерированный файл из OpenAPI. Не должен быть в git.

**Рекомендация:** Добавьте в `.gitignore` и генерируйте при сборке (`npm run codegen`).

### 20. Нет виртуализации длинных списков

Списки документов и сообщений могут быть длинными.

**Рекомендация:** Используйте `react-window` или `@tanstack/react-virtual` для виртуализации списков в `documents/` и `chat/`.

## Приоритет

Если брать топ-3 для немедленного действия:

1. **Разбить `rag_service.py` и `paperqa_service.py`** — улучшит поддерживаемость
2. **Добавить SSE для прогресса задач** — снизит нагрузку, улучшит UX
3. **Добавить версионирование `document_chunks`** — предотвратит потери данных при миграциях
