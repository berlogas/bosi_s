## 3. Дефекты

### D1. Purge сессии удаляет файлы глобальной базы — потеря данных · критично

Цепочка:

1. `core/safety.py:28-32` — корни импорта сессии: `sessions_dir/<id>` **и** `documents_dir`
   (каталог глобальной базы). Это осознанное поведение, оно зафиксировано тестом
   `tests/test_hardening.py:51 test_shared_documents_dir_is_allowed`.
2. Исследователь добавляет такой файл в сессию → `session_documents.py:210` → `_register`
   пишет в `documents.path` **путь глобального файла** (`paperqa_service.py:286`).
3. `db/repositories/documents.py:320 session_document_paths` возвращает **все** пути
   документов сессии, не различая «свой файл» и «общий файл».
4. `workers/reaper.py:41 remove_files` делает `path.unlink()` по каждому пути.

Итог: при истечении TTL сессии (архив → purge) reaper **удалит файл глобальной базы**.
Запись в реестре и индекс PaperQA останутся — глобальный документ превратится
в битую ссылку на несуществующий файл.

Проверка на стенде (не разрушающая):

```
файл глобальной базы: /data/documents/library/2026-10/ref1_chlorophyll.md
существует: True
ИМПОРТ РАЗРЕШЁН -> /data/documents/library/2026-10/ref1_chlorophyll.md
внутри documents_dir: True
```

**Где чинить:** `session_document_paths` должен возвращать только файлы, принадлежащие
сессии (путь внутри `sessions_dir/<id>`); либо `remove_files` должен проверять
принадлежность каталогу сессии через `core/safety.ensure_within`.

### D2. `bulk_async` использует сессию БД из HTTP-запроса · критично

`api/documents.py:263-314`: замыкание `body(task)` захватывает `db` (сессию
зависимости FastAPI) и `admin`. Ответ возвращается сразу, `get_db` закрывает
сессию в `finally`, а фоновая задача продолжает её использовать — параллельно
с потоком запроса, который в это время пишет `audit(db, …)`.

Сессии SQLAlchemy не потокобезопасны; граница транзакции не определена
(`upsert_document` делает `db.commit()` — он может закоммитить изменения запроса).
Для фоновых задач в проекте есть `db/session.py:session_scope()` — он здесь не используется.

**Где чинить:** внутри `body` открывать свою сессию через `session_scope()`.

### D3. Индексация в сессии синхронная — требование ТЗ не выполнено · существенно

`PHASE10_ACCEPTANCE.md` §3.1: «Индексация запускается асинхронно; progress visible в UI».

- `api/session_documents.py:135-178` — `POST .../documents/upload` ждёт полную индексацию
  внутри HTTP-запроса (таймаут клиента 600 с). Индексация PDF занимает секунды-минуты.
- Бэкенд умеет асинхронно: `api/documents.py:263 POST /api/admin/documents/bulk-async`
  (задача + прогресс по файлам). Но он **не подключён к интерфейсу**, и для сессионной
  загрузки асинхронного варианта нет вообще.
- В интерфейсе виден только прогресс передачи байтов (XHR `onProgress`), а не индексации.

**Где чинить:** добавить асинхронный вариант сессионной загрузки (задача + `TaskPanel`)
и подключить существующий `bulk-async` в админке.

### D4. `duplicates` и `failed` теряются в интерфейсе · существенно

Бэкенд отдаёт `DocumentBatchResultOut {added, duplicates, failed}` — интерфейс их выбрасывает:

- `webapp/src/features/documents/DocumentsTab.tsx:457-458` — показывается только
  «Добавлено: N, ошибок: M»; тексты ошибок по каждому файлу из `failed` теряются.
- `webapp/src/features/admin/tabs/DocumentsPage.tsx:164-166` — при успехе не показано
  ничего, при ошибке — только ошибка транспорта.

Пользователь не узнаёт, что конкретный файл не проиндексировался и почему, и что
файл уже был в базе (дубликат). Требование «Ошибки индексации попадают в `failed`
поля ответа» формально выполнено на бэкенде, но пользователь их не видит.

**Где чинить:** в обоих экранах показывать список `failed` (файл + причина) и
отдельно — число дубликатов.

### D5. `force_reindex` не выведен в интерфейс; «переиндексация при изменении содержимого» не работает как пользовательский сценарий · существенно

- `force_reindex` есть в API (`api/documents.py:174`, `paperqa_service.py:227`), но
  фронтенд его никогда не отправляет — переиндексировать документ после смены настроек нечем.
- Требование `COMPLIANCE_PLAN` 1.3.2 («переиндексировать, если изменился контент») в
  пользовательском смысле не работает: `dockey` = MD5 **содержимого**, поэтому
  изменённый файл получает **новый** dockey → это **новый** документ, а старая версия
  остаётся и в индексе, и в реестре. `doc_version` растёт только при повторном
  добавлении того же содержимого (`upsert_document`).
- Мёртвый код во фронтенде: `webapp/src/features/admin/queries.ts:160 useBulkUpload`
  не используется; эндпоинты `bulk`, `bulk-upload`, `bulk-async` бэкенда интерфейсом
  не вызываются.

**Где чинить:** (а) кнопка «Переиндексировать» для документа с передачей
`force_reindex`; (б) при загрузке файла с тем же именем — спросить «заменить
существующий документ?» и удалять старую версию; (в) удалить `useBulkUpload`.

### D6. Временные файлы загрузки не удаляются · существенно

`paperqa_service.py:299-341 add_uploads` пишет `uploads/{uuid}_{name}` и **не удаляет
файл**, если `add_file` вернул `None` (дубликат) или бросил исключение. Файл остаётся
навсегда. Проверено на стенде: повторная загрузка того же файла оставила лишний файл
в `documents/uploads` (я его убрал).

Там же: `add_url` (`:343-396`) удаляет скачанный файл только при сетевой ошибке;
если `add_file` падает (например, неподдерживаемое расширение) — файл остаётся.

**Где чинить:** удалять временный файл в `finally`, если документ не проиндексирован.

### D7. `add_file` определён дважды в одном классе · существенно

`paperqa_service.py:198` и `:219` — два определения `add_file`. Первое обрывается на

**Где чинить:** удалить первое определение (строки 198–217).

  сессионная загрузка работают через `session_scope()`; сессия запроса к моменту
  старта задачи уже закрыта, а общая сессия из двух потоков небезопасна.
  В замыкание попадают только простые значения (id, категория, теги) — ORM-объекты
  из закрытой сессии не переживают задачу.
- **Служба разделила сохранение и индексацию:** `stage_uploads()` (файлы на диск)
  и `index_staged()` (индексация + колбэк прогресса). Это нужно потому, что объект
  загрузки FastAPI закрывается вместе с ответом, а задача живёт дольше: файлы
  должны оказаться на диске до старта задачи.
- **Интерфейс:** `DocumentsTab` переключён на фоновую загрузку; панель задач с
  прогрессом уже была на месте (`useSessionIndexingTasks` + `TaskPanel`) — теперь
  она появляется. `useSessionIndexingTasks` обновляет список документов, когда
  индексация дошла до конца, и показывает итог: сколько проиндексировано, сколько
  дубликатов и какие файлы не разобрались (по причине).
- **D14 (найдено при разборе) — `bulk_async` не проверял пути.** В отличие от
  `bulk_add` он брал файлы как есть: админ мог проиндексировать любой файл на
  диске, обойдя `ALLOW_EXTERNAL_IMPORT_PATHS`. Теперь пути проверяются так же.

**Тесты:** backend — асинхронная загрузка (task_id, прогресс, документ в реестре),
плохой файл не роняет пачку, `bulk_async` регистрирует документы и отклоняет путь
вне разрешённых каталогов; frontend — фоновая загрузка уходит на `upload-async`
и панель задачи показывает этап, по завершении виден итог индексации.

**Проверка:** тест на пути проверен откатом проверки — без неё он падает.
На живом стенде: ответ `{"task_id": ..., "total": 1}` сразу, этапы

## 6. Что можно не делать

- **Асинхронная индексация админской пачки** (`bulk-async`) — эндпоинт готов и
  теперь работает без гонки за сессию БД, но в интерфейс админки не подключён.
  Если админ загружает десятки файлов, стоит подключить: сценарий тот же.
- **Вынос `add_url` в API** — в оффлайн-контуре внешние источники недоступны; метод
  можно удалить, если URL-импорт не планируется.
- **Полная «замена версии» документа** (D5, б) — можно ограничиться кнопкой
  «Переиндексировать» и подсказкой, если документов немного.
